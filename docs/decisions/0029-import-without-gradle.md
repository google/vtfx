# Sources that build without Gradle

- Status: Approved (2026-10-15, approved by a human in a review of the review queue. The direction was chosen by a human on 2026-10-14)
- Date: 2026-10-14
- Related: [0087](0087-public-api.md) (`@InternalVtfxApi`), [0079](0079-emulation-scope.md) (the character width tables), [0018](0018-distribution.md), [0023](0023-code-style.md), `build-logic`, `scripts/generate_unicode_tables.py`

## Background

An app may build the vtfx sources with another build system (for example Bazel), which compiles them with its own rules instead of the conventions in `build-logic`. Whatever the sources need from the Gradle build has to be written again there, and a missing compiler option shows up only as errors in an unfamiliar codebase.

The vtfx modules opted in to `@InternalVtfxApi` with a compiler option (`optIn` in the conventions `vtfx.jvm-library` and `vtfx.compose`), so none of them compiled without `-opt-in=com.google.vtfx.core.InternalVtfxApi`.

The character width tables of `vtfx-core` (`UnicodeWidthTables.kt`) were generated by a Gradle task in `build-logic` (`GenerateUnicodeWidthTablesTask`) into `build/`, so `vtfx-core` had a source that existed only in a Gradle build.

## Decision

### Opt-in in the sources

- Each file that uses declarations marked `@InternalVtfxApi` opts in with `@file:OptIn(InternalVtfxApi::class)`, in the main sources and in the tests. The conventions in `build-logic` no longer pass `optIn`. A file-level opt-in, rather than one per declaration, keeps the change mechanical and close to the module-wide opt-in it replaces.
- Apps still must not opt in. The sample app has no `@OptIn(InternalVtfxApi::class)`, so it still compiles with the public API alone.

### Committed generated sources

- The sources generated from the Unicode Character Database are committed like the other sources (the direction was chosen by a human): the character width tables (`UnicodeWidthTables.kt`) and the diacritics of the kitty graphics placeholders (`PlaceholderDiacritics.kt`) in `vtfx-core`, and the default-ignorable code points (`UnicodeDefaultIgnorables.kt`) in `vtfx-gate`. `scripts/generate_unicode_tables.py` generates them from the copies of the UCD files in `third_party/unicode`; there is no generation task in the Gradle build. It uses only the Python standard library, like the other scripts, and does not download anything. Its tests (`scripts/tests/test_generate_unicode_tables.py`) check the rules on small UCD files.
- `scripts/check.sh` runs `scripts/generate_unicode_tables.py --check`, which regenerates the files in memory and fails if a committed file differs, so the files cannot drift from the UCD files or be edited by hand.
- The generated files begin with the same Apache License header as the other sources, so the license header check covers them as it does every other source. The UCD files they are generated from stay under the Unicode License v3 in `third_party/unicode`, as [0018](0018-distribution.md) arranges for the artifacts that contain the tables. A human confirmed that this header is right for the generated files.
- ktfmt would break the tables of value pairs into one value per line, so `vtfx.ktfmt` excludes `UnicodeWidthTables.kt` and `UnicodeDefaultIgnorables.kt` by path ([0023](0023-code-style.md)). The `--check` above keeps their format fixed instead.

### What the sources still expect from the build

The conventions in `build-logic` were audited for compiler options that the sources need or that change what they mean. Apart from the opt-in, none of them is needed to compile the sources:

- **Explicit API mode** (`explicitApi()`) and **warnings as errors** (`allWarningsAsErrors`) only check the sources; they compile without them.
- **The JVM target** (17, also for Java) chooses the bytecode version; it does not change the meaning of the sources.

What another build system still has to provide, because the sources are written for it:

- **The Compose compiler plugin** for `vtfx-compose` (and the sample app), like any Compose code.
- **Tests that see `internal` declarations** of their module: each test source set (and the test fixtures of `vtfx-core`) is compiled as a friend of its main source set, which Gradle does for every test compilation (in Bazel, `associates` of `kt_jvm_test`).
- **The test environment**: some tests read the oracles in `spec/` and the recordings in `recordings/` through system properties (`vtfx.specDir`, `vtfx.recordingsDir`), and the tests of the Android modules run on Robolectric. This concerns only running the tests, not compiling the library.

No Kotlin language feature that needs a flag (context parameters, `-Xjvm-default`, and so on) is used.

## Alternatives considered

- **Keep generating the tables in the build, and give other build systems the script**: Every build system would have to run a generation step before compiling `vtfx-core`; with the file committed, they only list the sources.
- **Generate the tables at run time from the UCD files as resources**: Adds the UCD files to the artifact and parsing at startup, for data that changes once per Unicode version.
- **Format the generated file with ktfmt**: Doubles its length and loses the pairs of first and last code point that make it readable.
- **Keep the compiler option and document it**: Every build system that imports vtfx would have to set it on each module, and leaving it out gives errors that point at many files.
- **Opt in per declaration** (`@OptIn` on each function or class that uses a marked declaration): Shows more precisely where the internal API is used, but needs many more annotations, and new code would have to add them one by one.
- **Propagate the opt-in by marking the users `@InternalVtfxApi` too**: Would spread the marker to declarations that are not shared between modules, and change what the public API is.

## Impact of reversing

For the generated sources, delete the committed files and the `--check` step in `scripts/check.sh`, add a task that runs the script into `build/` and register its output as a source directory of `vtfx-core` and `vtfx-gate`, and drop the exclusions in `vtfx.ktfmt`.

For the opt-in, add `optIn.add("com.google.vtfx.core.InternalVtfxApi")` back to `compilerOptions` in `vtfx.jvm-library` and `vtfx.compose`, and remove the `@file:OptIn(InternalVtfxApi::class)` lines and their imports.
