# Sources that compile with Kotlin 2.0

- Status: Provisional
- Date: 2026-10-30
- Related: Section 7 of [architecture.md](../design/architecture.md), section 9 of [testing.md](../design/testing.md), [0087](0087-public-api.md), [0088](0088-build-boundaries-and-tests.md), `vtfx.jvm-library`, `vtfx.android-library`, and `vtfx.android-application` in `build-logic`

## Background

Other build systems may build the vtfx sources with a Kotlin compiler of their own rather than the one of the Gradle build ([0088](0088-build-boundaries-and-tests.md)), and that compiler can lag far behind: on 2026-10-30, `platform/external/kotlinc` of the public AOSP `main`, for example, held Kotlin 2.0.21 (upgraded on 2024-10-25), while vtfx builds with Kotlin 2.4.21. Nothing kept the sources from using a language feature or a standard library API newer than 2.0, and such a use would have shown only in such a build, as errors in a codebase unfamiliar to whoever builds it. [0088](0088-build-boundaries-and-tests.md) topic 1 keeps the sources free of compiler options for the same reason. When this was decided, all modules, their tests included, already compiled with language and API version 2.0.

## 1. Language and API version 2.0

1. The conventions `vtfx.jvm-library`, `vtfx.android-library`, and `vtfx.android-application` compile every module, its tests, test fixtures, and fuzz targets included, with `languageVersion` and `apiVersion` 2.0. A language feature or a standard library API newer than 2.0 then fails the build, and so `scripts/check.sh`.
2. `-Xsuppress-version-warnings` silences the compiler's warning that language version 2.0 is deprecated, which `allWarningsAsErrors` would turn into an error. It silences only the warnings about the language and API versions.
3. `build-logic` keeps the defaults of its Kotlin: it configures the Gradle build, which other build systems do not use.
4. The conventions also set the JVM default methods mode to `enable` (`jvmDefault`), the default of Kotlin 2.2 and later. Language version 2.0 would otherwise bring back the mode of Kotlin 2.0, in which the methods with default bodies of `TerminalSessionListener` are abstract in the interface and implemented only in `DefaultImpls`, a change of the ABI that the dump in `api/` shows (topic 5 of [0087](0087-public-api.md)).
5. The compiled classes carry Kotlin metadata of version 2.0, so a newer Kotlin in the Gradle build no longer raises the Kotlin compiler that apps need to read vtfx's metadata (topic 5 of [0087](0087-public-api.md)).

**Why.** The check runs in every build, the IDE's included, so a newer feature fails where it is written rather than in such a build. 2.0 covers compilers as old as the one of the public AOSP `main`. The settings only restrict what the sources may use: the sources compile the same without them, so [0088](0088-build-boundaries-and-tests.md) topic 1 still holds.

What the settings do not check:

- **The compiler itself.** Kotlin 2.4 restricted to language version 2.0 is not Kotlin 2.0.21; a difference in how the two compilers infer types, or a bug of the older one, shows only with that compiler.
- **JVM default methods.** Kotlin 2.0 compiles the methods with default bodies of `TerminalSessionListener` in its own default mode, to another ABI (item 4). A build that compiles all of vtfx from the sources is consistent with itself; to match the ABI of vtfx compiled by Gradle, it passes `-Xjvm-default=all-compatibility`, the name of `enable` before Kotlin 2.2.
- **The versions of the libraries.** Compose and the other dependencies that such a build provides may be older than those in `gradle/libs.versions.toml`.
- **The unused return value checker.** `-Xreturn-value-checker` does not exist in Kotlin 2.0; it only checks, so a build without it compiles the sources ([0088](0088-build-boundaries-and-tests.md) topic 3).

**Alternatives considered.**
- **A second compilation with language version 2.0 in `scripts/check.sh` only**: The sources would compile twice, and the IDE and the usual build would still accept newer features, found only by the check.
- **Compile with Kotlin 2.0.21 itself** (the compiler version of the Kotlin Build Tools API): Also checks the compiler, but adds a second compiler to the dependencies under review, through an experimental API, and still does not check the libraries. It can be added later if the language version proves not enough.
- **Only document the version**: The gap would still show only in such a build.

**Impact of reversing.** Remove `languageVersion`, `apiVersion`, `-Xsuppress-version-warnings`, and `jvmDefault` from the three conventions, and the bullet in section 7 of [architecture.md](../design/architecture.md); the sources can stay as they are. When a later Kotlin stops supporting language version 2.0, upgrading Kotlin fails on these settings: then check again which compilers the sources need to support, and raise the version to the oldest that both support.
