## Background

Requirement 6.1 names three untrusted inputs (the host's output, pasted content, and the IME), asks that the code under security review be listed explicitly and the boundary be checked mechanically, and, from phase 4, that the check hold against changes written to get around it. The area decides who the adversaries are, what security review covers and how its scope is drawn, and the rules by which the repository records its design and its history: how decisions and design documents divide the work, and how the history is kept.

## 1. The adversaries are the inputs; changes to the code are mistakes

1. **The adversaries are the untrusted inputs** of requirement 6.1: the host's output, pasted content, and the IME. The code of vtfx is not an adversary: a change to it that breaks a property is a mistake, to be caught by the gate's checks, by types, by tests, and by review and audit afterward.
2. **The check of the module boundaries keeps holding against changes written to get around it**, for what it covers: where the capabilities are ([0088](0088-build-boundaries-and-tests.md), unchanged).
3. **How code outside review calls the gate is guarded against mistakes, not against changes written to get around it.** For each method that takes a caller's claim, the gate checks what it can from the values, also when the caller already does, and fails fast on what must not happen rather than repair it; types narrow what a caller can pass or see, where that costs little; the KDoc states the caller's contract, and tests pin both sides (section 5 of [architecture.md](../design/architecture.md), section 7 of [boundaries.md](../design/boundaries.md)).
4. **No measure that needs a trusted path or a proof of the user's action is taken** for these properties: no tokens of user activation, no reviewed replacement of the platform's menus, no split of modules only to keep reviewed code from unreviewed code. Such a measure is reconsidered only for a property where a mistake is likely and its effect severe, by a new decision.

The first measures under item 3: `HostWriter.sendText` refuses a line break, and `ImeEditor` sends Enter where a line break is committed (section 2 of [gate-policy.md](../design/gate-policy.md), section 4.2 of [ime-contract.md](../design/ime-contract.md)); the user's copy drops the characters that an OSC 52 write may not carry, and the pasted clipboard text stays in the gate as a `ClipboardText` that only `vtfx-gate` reads and that goes to `HostWriter.sendPaste` as one paste (section 4.2 of [gate-policy.md](../design/gate-policy.md)); the keys of scroll gestures are `TerminalKey`s (`TerminalSession.sendScrollKey`), which carry no text.

**Why.** Read widely, requirement 6.1 would make the code itself an adversary. Several methods of the gate believe what the caller claims: `HostWriter.sendText` that the text is what the user typed, on one line (whether committed text is a paste is decided in `ImeEditor`); `TerminalGate.copyToClipboard`, `readClipboardForPaste`, and `openUrl` that the user asked for them; and what the IME sees is decided by the `InputConnection` adapter in `vtfx-compose`, which holds the whole session. A change to a caller can break such a property without referring to anything that the boundary check restricts. These are properties of how values match the world outside the program (whether bytes are what the user typed, whether the user chose a menu item), which no value proves. Making them hold against a change written to break them takes proofs of the user's actions made only by reviewed code from the platform's callbacks, reviewed menus that replace the platform's, module splits so that the code that holds the screen reaches neither the IME's editing model nor the writer, rules that keep each module from the methods it does not need, a public API that asks apps for those proofs, and the review of `vtfx-session`, through which everything passes. Even then, what the user saw, which link a tap was on, and what code does with a proof it kept for later stay with review. The cost grows faster than the guarantee, and most of it guards the code against itself. The check of where the capabilities are, by contrast, is cheap and decides what code outside review can do at all. With the first measure, a mistake in deciding what is a paste fails instead of running lines one by one despite bracketed paste mode.

**Alternatives considered.**
- **Keep requirement 6.1 read as making the code an adversary, and bring every module into tiers of trust**, reviewing the shape of the authority that reviewed code hands to the rest: it needs everything listed above, changes the public API, and still leaves the properties of how values match the world with review.
- **Review the modules that call the gate whole** (`vtfx-session`, `vtfx-compose`): the scope of review grows several times, with code that changes often, and the guarantee is that of review.
- **Drop the check against changes written to get around it altogether**, back to the guardrails of phases 1 to 3: the check of where the capabilities are already works and costs little; dropping it would give up the one guarantee that holds by construction.

**Impact of reversing.** Requirement 6.1 would again read as making the code an adversary for every property, and the properties held by callers' contracts would need the measures of item 4. The measures under item 3 would stay useful: each checks in the gate, or narrows by a type, what a caller claimed.

## 2. Security review is focused, not limited

1. **No code of vtfx is exempt from review, for security as for anything else.**
2. **"Under security review" keeps its meaning**: the paths under `security_review` in `config/protected-paths.toml`, which are the gate modules, which hold the capabilities, and the build configuration, which decides what the checks cover. A human reviews them again, closely, after the review of each change, and [review-queue.md](../review-queue.md) tracks it (section 5 of [architecture.md](../design/architecture.md)). The list and the term do not change.
3. **The design keeps the effect of a mistake outside those paths small**, rather than claiming that the code does not matter: the boundary check keeps the capabilities out of that code, also against changes written to get around it ([0088](0088-build-boundaries-and-tests.md)); each gate checks what it receives rather than trust it (section 1 of [architecture.md](../design/architecture.md), section 1 of [gate-policy.md](../design/gate-policy.md), section 2 of [fonts.md](../design/fonts.md)); the properties that rest on callers' contracts are guarded as in topic 1; resource limits and what is shown are kept by tests and fuzzing.
4. **The module tables say whether a module is under security review ("Yes" or "No")**, not whether review is needed (section 2 of [architecture.md](../design/architecture.md), section 2 of [fonts.md](../design/fonts.md)).

**Why.** Topic 1 leaves several properties of requirement 6.1 to the contracts of code outside review: whether text is what the user typed, whether the user asked for a copy, a paste, or a URL, and what the IME and accessibility services see. A mistake in that code can break those properties, and resource limits and what the screen shows live in `vtfx-core` and `vtfx-compose` themselves. Saying that such code needs no security review is not true, and invites skipping the security side of its review. Because each gate checks what it receives, a mistake in `vtfx-core` can show the wrong thing but cannot send the host's strings back to it or use the clipboard against the policy, and a mistake in `vtfx-font` can make glyphs look wrong or reject a font but cannot let unverified bytes reach native code.

**Alternatives considered.**
- **Put every module under security review**: every change would wait for the closer review, and the review would be spread thin; topic 1 rejects reviewing `vtfx-session` and `vtfx-compose` whole for the same reason.
- **Keep saying that most code does not need security review**: it is untrue once changes to the code are mistakes rather than adversaries (topic 1).
- **Rename `security_review` and the term** (for example "focused review"): the key, `scripts/report_protected_changes.py`, its tests, and dozens of references would change, with no change in what is reviewed.

**Impact of reversing.** Restore the wording of requirements 2 and 6.1 that most of the code does not need security review, "Needed" and "Not needed" in the tables of architecture.md and fonts.md, and, in "A small, explicit security boundary" of [README.md](../../README.md), the item that said security review could focus on `vtfx-gate` and `vtfx-gate-android`, where the item "Review is focused, not limited" now stands.

## 3. Security review covers whole modules, named with `gate`, in reserved packages

1. **Security review covers whole modules.** `config/protected-paths.toml` lists code only as `<module>/**`, besides build configuration and scripts; no single source files. Code that needs review, and what it relies on, lives in a module of its own (section 2 of [architecture.md](../design/architecture.md)).
2. **The modules under review are named with `gate`**, as `vtfx-gate` and `vtfx-gate-android` are: a gate decides what may cross a boundary, whether to the host and the outside world or into the platform's native code.
3. **Each pair of gate modules keeps all its classes in a package of its own, which `config/boundaries.toml` reserves to it with its subpackages**: `com.google.vtfx.gate` for `vtfx-gate` and `vtfx-gate-android` (whose classes are in its subpackage `com.google.vtfx.gate.android`), and `com.google.vtfx.font.gate` for `vtfx-font-gate` and `vtfx-font-gate-android` (section 4.6 of [boundaries.md](../design/boundaries.md), section 2 of [fonts.md](../design/fonts.md)).

**Why.** What reviewed code relies on is not all in the files that hold it. The verifier's guarantee relied on `SanitizedFont.kt`, which holds the guarantee that a `SanitizedFont` passed the verifier (its private constructor, the one function that calls it, the copy that keeps the caller from changing bytes after the check, and the read-only buffer), where a factory added would skip the verifier without any review; and on `InvalidFontException.kt` and `FontLimits.kt`, shared with the readers and the writer, so that a change made for the readers changed the verifier unreviewed. A boundary drawn around files has to be redrawn by hand whenever code moves between them; a module boundary is enforced by the compiler (`internal`, `private`) and by `config/boundaries.toml`. A package split across modules would let any of them replace a reviewed class: a class that another module declares with the name of a reviewed one compiles, and replaces it wherever that module comes first on the class path, so that, for example, a copy of `SanitizedFont` whose `fromCanonical` skips the verifier would make malformed fonts pass, or another `com.google.vtfx.gate.Replies`, which builds every reply to the host, would replace the reviewed one. An Android app's build rejects the duplicate class when it merges dex files, but a JVM program that uses the modules without a UI does not.

**Alternatives considered.**
- **Keep listing single files under review** (adding `SanitizedFont.kt`, `InvalidFontException.kt`, and `FontLimits.kt`): the list would have to follow every refactoring by hand, and nothing would stop new code that the reviewed code relies on from landing in an unlisted file.
- **Guard a split package instead of reserving one**, so that public types keep their package: it would take either a rule in `config/boundaries.toml` against declaring each of their names elsewhere, which every new type and file of the gate module would have to extend by hand, or a check of the compiled classes of every module, a new task in `build-logic`.

**Impact of reversing.** List files again in `config/protected-paths.toml` and `config/boundaries.toml`; topic 4 says what moving the font code back takes.

## 4. The font modules are split around the verifier

1. `vtfx-font` is split in three: `vtfx-font-gate` (JVM, no dependencies, under review) holds the verifier and the public types that its guarantee relies on; `vtfx-font` (JVM, not under review) keeps the readers, the CFF interpreter, the curve approximation, the writer, and `FontFile`; `vtfx-font-gate-android` (Android, under review) holds the one file that makes typefaces from `SanitizedFont`s, and `config/boundaries.toml` allows the font APIs there alone (sections 2 and 8 of [fonts.md](../design/fonts.md), section 4.5 of [boundaries.md](../design/boundaries.md)).
2. **The verifier's tests are in `vtfx-font-gate`**, under review with the code that they check, with canonical fonts kept as files, a test in `vtfx-font` that checks that sanitizing still writes them byte for byte, and a fuzz test that changes them and computes their checksums again (section 10 of [fonts.md](../design/fonts.md)).
3. The public API changes accordingly (section 3 of [fonts.md](../design/fonts.md)), as [0087](0087-public-api.md) allows before 1.0 (0.1.0 was published only as the source repository, without artifacts or a tagged release, [0090](0090-distribution.md)): `SanitizedFont.sanitize` becomes `FontFile.sanitize`, beside `FontFile.inspect`, since `vtfx-font-gate` cannot call the readers, which depend on it, and it ends in `SanitizedFont.fromCanonical`, so the verifier stays the only way to a `SanitizedFont`; `InvalidFontException` gets a public constructor, since the readers throw it from another module (apps have no reason to construct one, and one that they construct proves nothing); `SanitizedFamily`, which `vtfx-font-gate-android` takes, moves from `com.google.vtfx.compose` to `com.google.vtfx.font.gate` in `vtfx-font-gate` and loses Compose's `@Immutable`, which no composable parameter relied on, since they have the type `TerminalFont`, which keeps it; and the public types of `vtfx-font-gate` move from `com.google.vtfx.font` to `com.google.vtfx.font.gate`, keeping their names, so that no package is split between `vtfx-font` and `vtfx-font-gate` (topic 3), so apps change their imports.
4. The split accepts two costs, described in section 11 of [fonts.md](../design/fonts.md): sanitizing holds one more copy of the output for a moment, and the ABI dump of `vtfx-font-gate-android` lists `SanitizedTypefaces`. Fixing either is a separate change.

**Why.** Only the code that decides what reaches native code is then under review, together with all that its guarantee relies on (topic 3), while the code where most changes happen is not. The verifier still shares no code with the readers: each has its own functions that throw. `vtfx-compose` derives the bold and italic typefaces from the regular one with `Typeface.create`, which reads no font data, so it needs no font APIs. The tests are under review so that a change that weakens them is reviewed too; they take fonts kept as files since `vtfx-font-gate` cannot depend on `vtfx-font`, even in its tests, and the fuzz test computes the checksums again so that the changed fonts reach the checks of every table rather than fail the first checksum, as almost all raw bytes do.

**Alternatives considered.**
- **Put the whole of `vtfx-font` under review**: one line in the configuration, but the readers, the charstring interpreter, and the curve approximation, where most changes happen, would all need security review, against the point of the separate verifier ([0086](0086-fonts.md)), and the review would be spread thin.
- **Other names**: `vtfx-font-canonical` or `vtfx-font-verifier` (accurate, but say nothing of review; the second is narrower than the contents), or keeping `vtfx-font` for the small module and renaming the readers `vtfx-font-sanitizer` (the fewest changes for apps, but the name does not say what is reviewed).
- **Keep the public types in `com.google.vtfx.font`, split across `vtfx-font` and `vtfx-font-gate`, so that apps keep their imports**: another module could then replace them, `SanitizedFont` included (topic 3).
- **Let the tests of `vtfx-font-gate` depend on `vtfx-font`**, so that they build the fonts that they check: `config/boundaries.toml` would need a dependency of `vtfx-font-gate` on `vtfx-font`, which the boundary check could not tell apart from one of the reviewed code on the code that it reviews, since tests have no list of their own ([0088](0088-build-boundaries-and-tests.md)).
- **Keep the verifier's tests in `vtfx-font`**: they would build their fonts, but a change that weakens them would not be reviewed, and the fuzz test there passes raw bytes, almost all of which fail the first check of a checksum.
- **Make `SanitizedTypefaces.regular` public API**, so that `vtfx-font-gate-android` needs no dependency on `vtfx-core`: apps would get an API that they do not need, which the public API check would then hold.

**Impact of reversing.** Merge `vtfx-font-gate` back into `vtfx-font` and `vtfx-font-gate-android` back into `vtfx-compose`; move `CanonicalVerifier` and the public types of `vtfx-font-gate` back to `com.google.vtfx.font`; restore `SanitizedFont.sanitize`, the internal constructor of `InvalidFontException`, and `SanitizedFamily` in `vtfx-compose`; list the files again in `config/protected-paths.toml` and `config/boundaries.toml`.

## 5. The git history is never rewritten after publication

1. From publication on (2026-10-15), the git history is never rewritten: no amending, rebasing, squashing, or force pushing of existing commits. Changes, including reverts, are added as new commits.
2. The history before publication was squashed into one commit, so the work before publication is not in the history.
3. Because commits are never rewritten, a commit's full SHA is a stable reference. Documents that are about commits name them by full SHA instead of retelling their changes.

An agent that finds that the history needs to be rewritten stops and consults a human ([AGENTS.md](../../AGENTS.md), "History" and "Situations in which to stop and consult").

**Why.** Others depend on the published commits staying as they are: clones and forks of the repository, `.git-blame-ignore-revs` ([0088](0088-build-boundaries-and-tests.md)), and documents that name commits by their SHA (review targets, and the base of a review range in [review-queue.md](../review-queue.md)).

**Alternatives considered.**
- **Allow rewriting the history to clean it up** (squashing fixups, rewording messages): every clone and fork would diverge from `main`, and the SHAs in `.git-blame-ignore-revs` and in the documents would point at commits that no longer exist on `main`.
- **Keep the history before publication**: a human chose to publish one squashed commit instead.

**Impact of reversing.** Clones and forks would need to be reset to the rewritten `main`. The SHAs in `.git-blame-ignore-revs`, review-queue.md, and the review reports in `docs/reviews/` would need to be found again in the rewritten history, and the "History" bullet of AGENTS.md would change.

## 6. Design documents describe the current design; decisions record why

1. **The design documents (`docs/design/`) are the only description of the current design.** When behavior changes, they change. Decisions link to the sections that describe what they decided, rather than describing it again. Where a decision held the only description, the description moves to a design document.
2. **A decision records why**: the background, what was decided, the alternatives, and the impact of reversing. Changes are not appended to it as dated notes (topic 7 says how a decision changes). Errors of fact (a wrong name, count, or path) are corrected in place, without a dated note. Measurements and research go in `docs/research/` or in commit messages, and how something came about goes in commit messages. A research document records what was measured at its date and is not kept up to date: what it led to is in the design documents.
3. **Files are not moved to new directories.** The existing paths (`decisions/`, `design/`, `research/`, and the files at the top of `docs/`) stay, and new design documents are added under `design/`.
4. **References are checked mechanically where they can be.** `scripts/check_doc_links.py`, run by `scripts/check.sh`, checks that cited paths and relative links exist. References to sections are not checked, so documents keep their section numbers and add new sections at the end.

**Why.** Decisions made up most of the size of `docs/`, and the size came less from the number of files than from what the decisions held. Where decisions were the only place that described the current behavior, and the design documents linked to them for it, every change of behavior edited an approved decision. Changes appended to old text as dated notes made a reader rebuild the current state from many decisions, and where a later decision changed an earlier one without a note, the earlier one silently contradicted the code. Measurements, experiment logs, and narratives of how something came about were mixed into the reasons. Code comments, scripts, and configuration cite documents by path and by section number, and `config/protected-paths.toml` lists some documents by path, so paths and section numbers have to stay.

**Alternatives considered.**
- **Keep decisions as living documents with dated corrections**: every change of behavior would go on edited approved records, and a reader would still rebuild the current state from the notes.
- **Reorganize the directories by audience** (`process/`, `history/`, a guide for users): the gain is small next to the cost: the paths in code comments, AGENTS.md, and `config/protected-paths.toml` (security review) would all change, and the size problem is in the contents of the decisions, not in where files are. Rejected for now; with the link check in place, it can be done later.
- **Move `research/` to an archive directory**: marking each research document as a record of its date gives the same signal without changing paths.

**Impact of reversing.** Specifications would move back from the design documents into the decisions, and changes would go back to dated notes. `scripts/check_doc_links.py` would stay useful on its own.

## 7. Decisions hold the current reasons; the history holds the past ones

1. **A decision holds the reasons that hold now.** When a decision changes, the decision is rewritten, or a new decision takes its place and the old one is deleted. No decision is kept with the status `Superseded` or `Withdrawn`, and no status names superseded items: a decision that is dropped with nothing in its place is deleted. The past versions are in the history (topic 5).
2. **Decisions about one area may be merged into one decision**, which is given a new number; the merged decisions are deleted. Numbers are never reused, so a deleted number stays unused.
3. **The status is per decision**: `Provisional` or `Approved`, for the whole file. Only a human approves a decision. A merge, or a rewrite, that keeps the meaning of everything it carries over (it reorders, removes repetition, removes descriptions of the current design that the design documents hold, or drops what was superseded) keeps the status `Approved` when every decision it carries over was approved; otherwise the result is `Provisional`. The commit says which decisions it carries over and that their meaning is kept.
4. **The change that deletes or renumbers a decision updates every reference to it** in the same commit. `scripts/check_doc_links.py` fails on a reference to a decision that does not exist.

The decisions written before this rule are merged area by area. Until a decision is merged, it keeps the status it has, superseded items included ([decisions/README.md](README.md)).

**Why.** Keeping a changed decision as a record with the status `Superseded by`, or with its superseded items named in its status, made a reader follow the status to the decisions that replaced some of its items, and read the old text knowing which parts no longer hold; and the reasons for one area were spread over many decisions written as the area grew. Since the history is never rewritten (topic 5), every past version of a decision can be read from the commit before it changed; closed review reports are removed from the tree on the same ground (section 3.4 of [reviews/README.md](../reviews/README.md)).

**Alternatives considered.**
- **Keep decisions as records that are never rewritten, and cut superseded decisions to a summary and a link**: removes the old text but not the decisions that only point elsewhere, and the reasons for one area stay spread over many files.
- **Status per item of a merged decision**: keeps an approval exact to the item, but a human would approve items one by one, and every item would carry a status line.
- **Move the reasons into the design documents and drop `docs/decisions/`**: the design documents are already large, and mixing why into what makes the current design harder to read.
- **Keep the old numbers, merging into the oldest decision of each area**: saves updating the references to that one decision, but the title and the scope of the decision change under a number that code comments cite for what it meant before.

**Impact of reversing.** Deleted decisions can be restored from the history, and statuses `Superseded by` written again. `scripts/check_doc_links.py` would check superseded statuses again.
