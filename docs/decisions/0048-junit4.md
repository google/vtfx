# Tests on JUnit 4

- Status: Approved (2026-10-21, approved by a human)
- Date: 2026-10-21
- Related: Sections 6 and 7 of [testing.md](../design/testing.md), [0003](0003-fuzzing-gate.md), [0028](0028-parallel-fuzzing.md), [0029](0029-import-without-gradle.md), `vtfx.jvm-library` and `vtfx.fuzz` in `build-logic`, `scripts/fuzz.sh`

## Background

The tests of the JVM modules ran on JUnit Jupiter, and those of the Android modules on JUnit 4, which Robolectric, the Compose test rule, and Roborazzi's rule require. The fuzz tests used Jazzer's JUnit integration (`@FuzzTest`), which exists only for Jupiter.

[0029](0029-import-without-gradle.md) made the sources build with another build system, such as Bazel. The test rules of such builds commonly run only JUnit 4 tests (for example Bazel's `java_test` and `android_local_test`). So an app that builds vtfx that way could run the Robolectric tests, but not the tests of the JVM modules, which are most of the tests, including the spec runners, the attacks on the gate, and the replay of the fuzzing corpus. The fuzz targets could only be run through JUnit, not by a fuzzing engine on its own.

Two frameworks in one repository also split the shared test code: `ExpectedFailures` in the test fixtures of `vtfx-core` returned Jupiter's `DynamicTest`, so `OfficialGoldensTest` in `vtfx-compose` implemented the same list again.

## Decision

1. **The tests of the library modules and the sample app run on JUnit 4.** The tests of `build-logic` stay on Jupiter: they test the Gradle build itself, which another build system does not use.
2. **Parameterized tests use TestParameterInjector.** It takes parameters per test method, and value providers can list data at run time (the spec cases, the recordings, the fuzzing corpus), so a spec runner keeps listing its cases, running them, and checking the expected failures in one class. JUnit 4's own `Parameterized` takes parameters per class.
3. **The Jupiter-only features are replaced** without changing what the tests check: nested test classes with `Enclosed`, time limits with `@Test(timeout = ...)` or a helper with the same limit, temporary directories with `TemporaryFolder`, and the failures of the spec runners that carry the expected and actual values with `ComparisonFailure`. Assertions use `kotlin.test`, which most tests already use.
4. **`ExpectedFailures` does not depend on a test framework**: it runs a case and throws an `AssertionError` when the case does not fail or pass as the list says, and `OfficialGoldensTest` uses it too.
5. **The fuzz targets are libFuzzer entry points**: an `object` with a `@JvmStatic fun fuzzerTestOneInput(data: ByteArray)`, in a `fuzz` source set of the module, which depends on the module and not on JUnit or Jazzer. Jazzer runs it on its own, and any other fuzzing engine or continuous fuzzing service for the JVM that takes this entry point can run the same code.
6. **The corpus of each target is a plain directory** with one input per file (`src/fuzz/corpus/<target>/`). The `test` task replays every file through the entry point, each with a time limit of 10 seconds, the limit at which fuzzing reports a hang. The replay is the deterministic gate of [0003](0003-fuzzing-gate.md), and the time limit keeps hangs on the corpus detected without relying on the per-input timeout of a fuzzing engine, which not every engine offers.
7. **The `fuzz` task runs Jazzer's own driver** instead of JUnit. Inputs that make a target fail are written into the corpus directory, as Jazzer's JUnit integration did, so that the replay checks them from then on ([0003](0003-fuzzing-gate.md)). The corpus that fuzzing grows is kept in `build/`, not in the corpus directory.

## Alternatives considered

- **Run everything on the JUnit Platform, with the vintage engine for the JUnit 4 tests**: One launcher in Gradle, but the tests of the JVM modules stay on Jupiter, so a build that runs only JUnit 4 still cannot run them, and the fuzz targets stay tied to JUnit.
- **Jupiter everywhere**: Robolectric has no Jupiter runner, so the Android modules would still need JUnit 4.
- **JUnit 4's `Parameterized` instead of TestParameterInjector**: No new dependency, but parameters are per class, so a class with differently parameterized methods would be split, and the check for stale entries of the expected failures would move out of the spec runner's class.
- **Keep `@FuzzTest` and add libFuzzer entry points beside them**: Two ways to run each target, and the replay would still need Jupiter.

## Impact of reversing

Put the Jupiter dependencies and `useJUnitPlatform()` back into `vtfx.jvm-library`, and rewrite the tests of the JVM modules with Jupiter's features. To go back to `@FuzzTest`, move the targets back into the tests, move the corpus to `<FuzzTest>Inputs/<method>/` in the test resources, and make the `fuzz` task a `Test` task again.
