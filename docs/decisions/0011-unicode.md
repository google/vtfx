# Unicode version, character width, grapheme clusters, fonts

- Status: Approved (2026-10-13, approved by a human in the final review); generating the width table in the build superseded by [0029](0029-import-without-gradle.md)
- Date: 2026-10-12
- Related: Requirement 5.2, section 8 (the policy on the Unicode version, Ambiguous width, and grapheme clusters), section 7 of [emulation.md](../design/emulation.md), `CharWidth`, `scripts/generate_unicode_tables.py`, [third_party/unicode](../../third_party/unicode/README.md), `BoxDrawing`

## Background

If the terminal and the host disagree on character widths, cursor positions shift and the screen breaks. Most apps on the host count widths with libc's `wcwidth()` (or their own table with the same rules). Requirement 5.2 asks for the policy on fullwidth, Ambiguous, grapheme clusters, and the Unicode version to be decided.

## Decision

The rules that result are in section 7 of [emulation.md](../design/emulation.md).

- **Width rules**: Generate the width table from the Unicode Character Database with the rules of glibc's `utf8_gen.py`, so that the widths agree with `wcwidth()` on hosts with the same Unicode version. The generator reads copies of the UCD files in `third_party/unicode` and does not download them, so as not to put load on unicode.org (decided by a human). The table is generated by `scripts/generate_unicode_tables.py` and committed ([0029](0029-import-without-gradle.md)).
- **Unicode version**: 16.0.0, the same as glibc 2.41 in Debian 13 when this was decided. Move to a newer version after the libc of major hosts does.
- **East Asian Ambiguous**: width 1 by default, since `wcwidth()` returns 1 in almost all locales (including ja_JP.UTF-8). `AmbiguousWidth.Wide` makes it 2, for users of vim's `ambiwidth=double` and the like on the host. Matching the host's setting is the app's responsibility, and is written in the KDoc.
- **Grapheme clusters**: count widths per code point, to match the sum of `wcwidth()` on the host, and attach zero-width characters to the preceding cell. A sequence of emoji joined with ZWJ therefore takes cells for each emoji: drawing it in 2 cells as one emoji would disagree with the width the host counted. As an exception, a pair of regional indicators (a flag) is combined into one 2-cell character: the two indicators take 1 + 1 cells anyway, so combining them does not change the number of cells, and they can be drawn as a flag. A mode that counts a grapheme cluster as one unit (the mode 2027 proposal) is not supported, since it needs agreement with the host.
- **Box-drawing and block elements** are drawn as shapes rather than font glyphs, since font glyphs do not reach the edges of the cell and leave gaps between cells.
- **CJK characters** are drawn with Android's system font fallback, and the glyphs of Han characters (which differ between Japanese, Chinese, and Korean) can be chosen with `TerminalStyle.locale`, defaulting to the system locale. Robolectric's rendering could not show the difference, so checking on devices is in the review queue.

## Alternatives considered

- **Use the latest Unicode (18.0)**: The widths of newly assigned characters would disagree with the host. The libc of major hosts is still at 16 or earlier.
- **Draw a grapheme cluster as one unit**: Looks nicer, but disagrees with the width the host counted and breaks the cursor.

## Impact of reversing

To change the version, replace the files in `third_party/unicode` as its README describes, regenerate the table with `scripts/generate_unicode_tables.py`, and check the width examples in `EmulationCoverageTest`. To change the handling of grapheme clusters, change `Emulator.print` and `Line`, and section 7 of [emulation.md](../design/emulation.md).
