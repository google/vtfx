## R1: `TerminalGate.isAllowedUrl` allows backslashes in the authority prefix and malformed special-scheme URLs where `android.net.Uri` and browsers disagree on the host

- Related: [TerminalGate.kt](../../vtfx-gate/src/main/kotlin/com/google/vtfx/gate/TerminalGate.kt) (`isAllowedUrl`, `hasMisleadingAuthority`), [AndroidUrlOpener.kt](../../vtfx-gate-android/src/main/kotlin/com/google/vtfx/gate/android/AndroidUrlOpener.kt) (`open`)
- Contract: requirement 6.1 of [REQUIREMENTS.md](../REQUIREMENTS.md) (spoofed links and opening unintended URLs), section 5.2 item 5 of [gate-policy.md](../design/gate-policy.md) ("the authority has no `@` (userinfo), no `\`, no `%`, and no character that is not ASCII ... Browsers treat `\` in the authority as `/` but other parsers do not, so they disagree on the host"), item 7 of [decisions/0006](../decisions/0006-gate-defaults.md), and the KDoc of `TerminalGate.openUrl` ("Returns ... `OpenUrlResult.NotAllowed` without calling it if the scheme is not allowed, the URL is malformed, it has characters, userinfo, or a host that is not ASCII that could make the URL shown differ from where it goes")
- Reproduction test: `specialSchemeUrlsWithBackslashOrMissingDoubleSlashInAuthorityAreRejected`

Steps:

1. Call `TerminalGate(HostWriter {}).isAllowedUrl(url)` (or `openUrl(url)`) with special-scheme URLs that have `\` in the prefix after `:`, lack `//`, have three slashes, or have an empty host:
   - `"https://\\evil.example"`
   - `"https:\\\\evil.example"`
   - `"https:/\\evil.example"`
   - `"https:///evil.example"`
   - `"https:/evil.example"`
   - `"https:evil.example"`
   - `"https://"`

Expected result: `false` (`OpenUrlResult.NotAllowed`) for each URL.

Actual result: `true` for all of them (`java.lang.AssertionError: https://\evil.example`).

View of the cause: `hasMisleadingAuthority` starts with `while (i < url.length && (url[i] == '/' || url[i] == '\\')) i++` before scanning up to `/`, `?`, or `#`. That initial loop silently skips any number of `\` and `/` after `:` instead of rejecting `\` or requiring `//` followed by a non-empty host. As a result:

- For `"https://\\evil.example"`, `android.net.Uri.parse` (and RFC 3986) parses the authority and host as `"\\evil.example"`, and for `"https:\\\\evil.example"` `android.net.Uri.parse` parses the URI as opaque (`isOpaque == true`, `host == null`), whereas browsers (the WHATWG URL Standard) treat `\` as `/` and navigate to host `"evil.example"`.
- For `"https:///evil.example"` and `"https:/evil.example"`, `android.net.Uri.parse` and RFC 3986 parse an empty/null authority (`host == null`) with path `"/evil.example"`, and for `"https:evil.example"` `android.net.Uri.parse` parses an opaque URI (`host == null`), whereas browsers ignore all leading slashes after `:` in special schemes and navigate to host `"evil.example"`. In addition, when the scheme has an uppercase letter (e.g. `"HTTPS:///evil.example"` or `"HTTPS://"`), `Uri.parse(url).normalizeScheme()` in `AndroidUrlOpener` rebuilds the `Uri` without `//` (turning `"HTTPS:///evil.example"` into `"https:/evil.example"` and `"HTTPS://"` into `"https:"`) because `Uri` sees a null authority.
- For `"https://"`, `"https:///path"`, `"https://?q"`, and `"https://#f"`, the host is empty, which is a parse error (failure) in the WHATWG URL Standard.

Direction of the fix: for the special schemes (`http`, `https`, `ftp`, `ws`, `wss`), check that the scheme and `:` are followed by `//` and a non-empty host/authority before the first `/`, `?`, or `#` (so that zero, one, or three slashes, any `\` right after `:` or `/`, and empty hosts such as `https://`, `https:///path`, and `https://:80` are rejected). Also check the corresponding wording in section 5.2 item 5 of [gate-policy.md](../design/gate-policy.md), which currently says "with or without `//`".

## R2: `TerminalGate.handle` skips an allowed OSC 52 write before an allowed OSC 52 read when another allowed write follows in the same `feed`

- Related: [TerminalGate.kt](../../vtfx-gate/src/main/kotlin/com/google/vtfx/gate/TerminalGate.kt) (`handle`, `readClipboard`)
- Contract: the KDoc of `TerminalGate.handle` ("Handles the `[events]` that the terminal model emitted for one write of host output, in order: replies to queries and decides on clipboard requests"), section 4.1 of [gate-policy.md](../design/gate-policy.md), and item 4 of [decisions/0059](../decisions/0059-osc52-limits.md) ("the earlier writes would be replaced at once anyway. Like titles, only the latest value counts")
- Reproduction test: `osc52ReadBetweenTwoWritesInOneFeedRepliesWithThePrecedingWrite`

Steps:

1. Create a `TerminalSession` with `GatePolicy(allowClipboardWrite = true, allowClipboardRead = true)` and a `ClipboardAccess` holding `"secret from another app"`.
2. In a single `session.feed(...)` call, feed `OSC 52 ; c ; <base64("first")> BEL`, followed by `OSC 52 ; c ; ? BEL`, followed by `OSC 52 ; c ; <base64("second")> BEL`.

Expected result: the reply to the OSC 52 read carries `"first"` (`\u001b]52;c;Zmlyc3Q=\u001b\\`), and the clipboard holds `"second"` after `feed` returns — the same result as when the same byte stream arrives split across two `feed` calls.

Actual result: the reply to the OSC 52 read carries `"secret from another app"` (`expected:<[]52;c;Zmlyc3Q=\]> but was:<[]52;c;c2VjcmV0IGZyb20gYW5vdGhlciBhcHA=\]>`).

View of the cause: `TerminalGate.handle` computes `lastWrite = events.indexOfLast { it is TerminalEvent.ClipboardWriteRequested && mayWriteClipboard(it.selection, it.text) }` and performs `clipboard?.write(event.text)` only when `index == lastWrite`. Every earlier allowed `ClipboardWriteRequested` in the same `events` list is ignored, so an allowed `ClipboardReadRequested` before `lastWrite` reads the system clipboard from before `handle` was called instead of the text written by the preceding allowed `ClipboardWriteRequested`.

Direction of the fix: keep at most one `clipboard.write` call per `handle` (the last allowed write, so the OS clipboard preview is not triggered repeatedly), while ensuring that an allowed `ClipboardReadRequested` after an earlier allowed `ClipboardWriteRequested` in the same `handle` call observes that write (including its length check against `maxClipboardReadLength` and when the final write in the batch is rejected by `mayWriteClipboard` or occurs after the read).

## R3: `Replies.color` calls `ReportedColors.rgb` before checking the range of a palette index

- Related: [Replies.kt](../../vtfx-gate/src/main/kotlin/com/google/vtfx/gate/Replies.kt) (`color`, `graphics`), [TerminalStyle.kt](../../vtfx-compose/src/main/kotlin/com/google/vtfx/compose/TerminalStyle.kt) (`reportedColors`)
- Contract: section 3 of [gate-policy.md](../design/gate-policy.md): "Every number in a reply is checked against its range before the reply is built (positions up to `TerminalLimits.MAX_DIMENSION`, sizes in pixels up to that times `ProtocolLimits.MAX_CELL_SIZE`, palette indexes 0 to 255); a number out of range is a programming error."
- Reproduction test: `paletteIndexOutOfRangeIsCheckedBeforeCallingReportedColors`

Steps:

1. Call `HostWriter.sendReply(TerminalQuery.Color(ColorTarget.Palette(256)), colors)` with a `ReportedColors` that indexes a 256-entry palette array (as `TerminalColors.reportedColors` does in `vtfx-compose`).
2. Call `HostWriter.sendReply(TerminalQuery.Color(ColorTarget.Palette(256)), colors = null)`.

Expected result: both calls throw `IllegalArgumentException` from `Replies` before `colors.rgb` is called.

Actual result: step 1 throws `ArrayIndexOutOfBoundsException: Index 256 out of bounds for length 256` from `colors.rgb`, and step 2 returns without throwing (`Expected an exception of class java.lang.IllegalArgumentException to be thrown, but was completed successfully`).

View of the cause: `Replies.color` calls `val rgb = colors?.rgb(target) ?: return null` at line 161 before `require(target.index in 0..255)` at line 174. When `colors` is `null` (or returns `null`), the range check is never reached; when `colors` is `TerminalColors.reportedColors`, `indexed[target.index]` is indexed with the unchecked value first.

Direction of the fix: validate `target.index in 0..255` in `Replies.color` before calling `colors?.rgb(target)` (and check negative indexes such as `-1` as well). Also check `Replies.graphics` ([Replies.kt](../../vtfx-gate/src/main/kotlin/com/google/vtfx/gate/Replies.kt)): section 9.2 of [emulation.md](../design/emulation.md) states that a graphics reply is sent only when the command has an image id (`i`) or number (`I`), whereas `Replies.graphics` currently accepts `imageId == 0L && imageNumber == 0L` and builds `ESC _ G ; OK ESC \`.

## R4: `AndroidClipboard` throws `NullPointerException` when `ClipboardManager` is unavailable

- Related: [AndroidClipboard.kt](../../vtfx-gate-android/src/main/kotlin/com/google/vtfx/gate/android/AndroidClipboard.kt) (`clipboard`, `write`, `read`), [Capabilities.kt](../../vtfx-gate/src/main/kotlin/com/google/vtfx/gate/Capabilities.kt) (`ClipboardAccess`)
- Contract: the KDoc of `ClipboardAccess`: "Implementations must be thread-safe and must not throw. ... Returns the text on the clipboard, or null if there is none or it cannot be read."
- Reproduction test: `androidClipboardDoesNotThrowWhenClipboardServiceIsUnavailable`

Steps:

1. Construct `AndroidClipboard(context)` with a `Context` whose `getSystemService(ClipboardManager::class.java)` returns `null`.
2. Call `clipboard.write("copied")` and `clipboard.read()`.

Expected result: `write` returns without throwing, and `read` returns `null`.

Actual result: `write` throws `java.lang.NullPointerException: Cannot invoke "android.content.ClipboardManager.setPrimaryClip(android.content.ClipData)" because "this.clipboard" is null` (and `read` likewise dereferences `clipboard.primaryClip`).

View of the cause: `Context.getSystemService(Class<T>)` is `@Nullable` on Android, and `AndroidClipboard` stores the result without a nullability annotation (a Kotlin platform type `ClipboardManager!`) and dereferences it unconditionally in `write` and `read`.

Direction of the fix: type `clipboard` as `ClipboardManager?` in `AndroidClipboard`, make `write` a no-op when `clipboard == null`, and return `null` from `read` when `clipboard == null`. Also check whether `ClipboardManager.setPrimaryClip` or `primaryClip` can throw `SecurityException` or `IllegalStateException` on OEM/restricted builds when the app loses focus mid-call.

## R5: `TerminalSession.feed` calls `TerminalGate.handle` outside any lock after notifying `TerminalSessionListener`

- Related: [TerminalSession.kt](../../vtfx-session/src/main/kotlin/com/google/vtfx/session/TerminalSession.kt) (`feed`), [HostConnection.kt](../../vtfx-gate/src/main/kotlin/com/google/vtfx/gate/HostConnection.kt), [TerminalGate.kt](../../vtfx-gate/src/main/kotlin/com/google/vtfx/gate/TerminalGate.kt) (`handle`)
- Contract: the KDoc of `HostConnection` ("The calls are serialized in the order of the input, with locks held that only serialize them, so that sequences are not interleaved; no lock that guards the state of vtfx is held"), the KDoc of `TerminalSessionListener` ("Called on the thread that called `TerminalSession`, without holding the session's lock, so it may call the session"), the KDoc of `TerminalSession` ("Thread-safe: every method may be called from any thread, and the calls are serialized"), and section 2 of [session-and-threads.md](../design/session-and-threads.md)
- Reproduction test: `repliesAreSentInInputOrderWhenListenerCallsSessionDuringFeed`

Steps:

1. Create a `TerminalSession` whose `TerminalSessionListener.onBell()` calls `session.feed("\u001b[>c".toByteArray())` (DA2 query).
2. Call `session.feed("\u0007\u001b[5n".toByteArray())` (BEL followed by DSR 5 query).

Expected result: the reply to DSR 5 (`\u001b[0n`), which was fed in step 2 before `onBell()` fed DA2, is sent to `HostConnection` before the reply to DA2 (`\u001b[>0;10;1c`).

Actual result: the reply to DA2 is sent before the reply to DSR 5 (`expected:<[[0n, [>0;10;1c]> but was:<[[>0;10;1c, [0n]>`).

View of the cause: in `TerminalSession.feed`, `requests` are drained from `terminal` inside `lock.withLock`, then `lock` is released, `listener.onBell()` and `titleNotifier.tell()` are called, and only afterwards does `gate.handle(requests)` run, without any lock serializing `gate.handle`. Consequently:

- When `onBell()` or `onTitleChanged()` calls back into `session` (`feed`, `sendKey`, `sendText`, and so on, as `TerminalSessionListener` explicitly allows), the nested call's gate operations (`writer.sendReply`, `writer.sendKey`, `clipboard.write`) execute before the outer `feed`'s `gate.handle(requests)`, reversing the order of replies and OSC 52 writes relative to the terminal state transitions.
- When two threads call `session.feed(chunk1)` and `session.feed(chunk2)` concurrently, `chunk1` can update `terminal` under `lock` first, but `chunk2` can reach `gate.handle` first after releasing `lock`, sending `chunk2`'s replies before `chunk1`'s replies or letting `chunk1`'s older OSC 52 `clipboard.write` overwrite `chunk2`'s newer OSC 52 `clipboard.write`.

Direction of the fix: ensure that the gate side effects of `feed` execute in the order in which chunks are applied to the terminal and before listener notifications that can trigger subsequent session actions, while still respecting the rule in [decisions/0024](../decisions/0024-thread-conventions.md) and `HostConnection` that no lock guarding `vtfx`'s terminal state (`TerminalSession.lock`) is held while calling `HostConnection`, `ClipboardAccess`, `ReportedColors`, or `TerminalSessionListener`.
