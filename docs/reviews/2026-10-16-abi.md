# 2026-10-16 Gaps in the ABI check found in a review of binary compatibility

- Review target: `919b29e9a753ec6cd0bfa52ce7e53105ba744e02` (the whole tree; its public API is the same as `v0.1.0`)
- Reviewer: a coding agent (Jetski), in a session separate from the one that wrote the code
- Points of view: binary compatibility of the public API. Mainly 3 of 2.2 in [README.md](README.md): whether the ABI check fulfills requirement 6.5 and the compatibility check of [0016](../decisions/0016-public-api.md). The shape of the API that would make compatible changes hard after 1.0 was also reviewed; those parts are not bugs and are listed at the end.

Reproduced 2 bugs with 7 test cases. This review did not change product code.

## Running the reproduction tests

The reproduction tests are in [repro-2026-10-16-abi/](repro-2026-10-16-abi/). Run them from the root of the repository.

```sh
python3 docs/reviews/repro-2026-10-16-abi/abi_check_gaps.py
```

The findings are about the ABI check, not about the behavior of the library, so the reproduction is a script instead of the Gradle init script of 2.3 in [README.md](README.md). It exports the commit (`HEAD`, or the one given as the argument) to a temporary directory with `git archive`, and in that copy changes one public declaration per case and runs `checkKotlinAbi` of the module, which is expected to fail. A case fails when the check passes. A control case (a property added to `TerminalModes`) must be detected first, so that a passing check means a gap and not a broken setup. For R1, the script also compiles a small client against the unchanged library and runs that same client binary against the changed library. The repository is not modified.

At the target commit, the result is **7 cases, 7 not detected** (exit status 1), and the client throws for both changes of R1:

```text
control: detected, as expected
R1 default-value-removed: NOT DETECTED
R1 const-value-changed: NOT DETECTED
R2 type-argument-changed: NOT DETECTED
R2 return-made-nullable: NOT DETECTED
R2 parameter-renamed: NOT DETECTED
R2 fun-interface-removed: NOT DETECTED
R2 sealed-removed: NOT DETECTED
7 cases, 7 not detected
The same client binary against the unchanged library:
  default-value-removed: ok
  const-value-changed: ok
The same client binary against the changed library:
  default-value-removed: java.lang.IllegalArgumentException: columns out of range: 0
  const-value-changed: java.lang.IllegalArgumentException: columns out of range: 2048
```

It needs what the build needs (JDK 21 and the Android SDK in `local.properties`) and `java` on the `PATH`, and takes about 30 seconds with a warm Gradle cache. No emulator is needed. All cases are in JVM modules; the Android modules use the same dump format (`DumpAbiTask` in `build-logic`), but no case was run on them.

## R1: Changes that break apps compiled earlier pass the ABI check

- Related: `abiValidation` in [vtfx.jvm-library.gradle.kts](../../build-logic/src/main/kotlin/vtfx.jvm-library.gradle.kts), `DumpAbiTask` in [AbiDump.kt](../../build-logic/src/main/kotlin/AbiDump.kt), `api/<module>.api` of each library module
- Contract: requirement 6.5 ("Mechanically detect changes to the public API (including binary compatibility) and report them in CI"); "Compatibility policy" of [0016](../decisions/0016-public-api.md) ("changes to the public API are always detected by the check and appear in commits as differences in the dump")
- Reproduction test: cases `default-value-removed` and `const-value-changed`, and the client run

Steps:

1. Remove the default value of `columns` of the `TerminalSession` constructor (`columns: Int = DEFAULT_COLUMNS` to `columns: Int`), and run `:vtfx-session:checkKotlinAbi`.
2. Change `TerminalLimits.MAX_DIMENSION` from 2048 to 1024, and run `:vtfx-core:checkKotlinAbi`.
3. Run a client compiled against the unchanged library, which calls `TerminalSession(connection)` and `resize(TerminalLimits.MAX_DIMENSION, 24)`, against the changed library.

Expected result: the check fails for both changes, because both break apps that are not recompiled, and so the dump must differ.

Actual result: the check passes for both, and `api/` stays the same. The client throws `IllegalArgumentException: columns out of range: 0` from the constructor, and `IllegalArgumentException: columns out of range: 2048` from `resize`.

View of the cause: the dump lists the JVM descriptors of public methods and fields, which do not hold either change.

- A default value is applied by the synthetic `$default` method (here the constructor with a bit mask and `DefaultConstructorMarker`). Its descriptor stays the same as long as one parameter of the function keeps a default. A caller compiled earlier still sets the bit for `columns`, and the new body no longer replaces the placeholder 0 with the default.
- A `const val` is copied into the caller's bytecode at compile time. The dump has the field (`public static final field MAX_DIMENSION I`) but not its value. Lowering a bound that vtfx checks with `require` makes callers compiled earlier throw. vtfx-compose also copies `TerminalLimits.MAX_DIMENSION` (`Terminal.kt`, `TerminalRenderer.kt`), so the same applies between vtfx artifacts of different versions.

Direction of the fix: the check should report these changes in `api/` or fail on them. Surrounding cases to check:

- The other parameters with defaults: the rest of the `TerminalSession` constructor, `feed`, `snapshot`, `CharWidth.of`, and the constructors and `copy` of `GatePolicy`, `TerminalLimits`, `TerminalStyle`, `TerminalColors`, and `TerminalFont.*`. The composables `Terminal` and `rememberTerminalState` take the default mask in the same method (`Composer;II`), which removing a default does not change either (not run).
- Adding a default where the function already has one, which old callers do not see but which is a change to the public API (source-compatible).
- All public constants: `CharWidth.UNICODE_VERSION`, `TerminalLimits.MAX_DIMENSION`, `MAX_SCROLLBACK_LINES`, `MAX_STRING_LENGTH`, `GatePolicy.DEFAULT_MAX_CLIPBOARD_WRITE_LENGTH`, and `TerminalSession.DEFAULT_COLUMNS` and `DEFAULT_ROWS`. Whether a value that may change should be a `const val` at all is in "Observations that are not bugs" below.

## R2: Changes to the Kotlin signature of the public API pass the ABI check

- Related: the same as R1
- Contract: the same as R1. Requirement 6.5 asks for changes to the public API to be detected, binary compatibility included, not binary compatibility only; 0016 says that changes to the public API always appear as differences in the dump.
- Reproduction test: cases `type-argument-changed`, `return-made-nullable`, `parameter-renamed`, `fun-interface-removed`, and `sealed-removed`

Steps (one change per case, each followed by `checkKotlinAbi` of its module):

1. `GatePolicy.urlSchemes` from `Set<String>` to `Set<CharSequence>`.
2. `TerminalSession.title` from `String` to `String?`.
3. The parameter of `TerminalSession.canOpenUrl` from `url` to `link`.
4. `UrlOpener` from `fun interface` to `interface`.
5. `KeyStroke` from `sealed interface` to `interface`.

Expected result: the check fails for each change.

Actual result: the check passes for each, and `api/` stays the same.

View of the cause: the dump format (KGP's ABI validation for the JVM, the format of binary-compatibility-validator, which `DumpAbiTask` also writes) holds erased JVM descriptors and access flags. Type arguments, nullability, parameter names, and modifiers that live only in the Kotlin metadata (`sealed`, `fun`) are not in it. Each change still affects apps:

- Type arguments: code compiled against `Set<String>` casts the elements to `String`, so changing what the collection holds throws `ClassCastException` in apps that are not recompiled. The same goes for `TerminalColors.palette` (`List<Color>`), the `linkPatterns` of `Terminal`, and its callbacks `onLinkClick`, `onContextClick`, and `onPreImeKeyEvent`, whose types are all erased to `Function1`.
- Nullability: Kotlin does not check values returned by Kotlin code, so a `null` from a getter declared non-null before ends in a `NullPointerException` later in the app. A parameter made non-null throws in `checkNotNullParameter` for callers that pass `null`.
- Parameter names, `fun interface`, and `sealed`: calls with named arguments, SAM-converted lambdas, and exhaustive `when` stop compiling (source compatibility).

Direction of the fix: surrounding cases to check: the type arguments of parameters, return types, and supertypes; changes of nullability in both directions; the other Kotlin-only modifiers (`data`, `value`, `operator`, `infix`); and that the check of the Android modules gets the same fix as the JVM modules.

## Unverified concerns

- Compose-specific ABI: whether removing `@Immutable` from `TerminalStyle` or `TerminalColors`, or changing whether `Terminal` is restartable or skippable, affects callers compiled earlier. The dump has the `$stable` fields but not their values. Not investigated.
- The Kotlin version that apps need: the modules are compiled with Kotlin 2.4.21 without `languageVersion` or `apiVersion`, so the metadata is 2.4, and an app needs a Kotlin compiler that can read it. Upgrading Kotlin raises that minimum without any difference in `api/`. Not checked with an older compiler, and [usage.md](../usage.md) does not state a minimum.
- The methods with default bodies of `TerminalSessionListener` are JVM default methods plus `DefaultImpls`, by the default `-jvm-default` mode (`enable`) of Kotlin 2.2 and later. [0029](../decisions/0029-import-without-gradle.md) lets other build systems compile the sources; a Kotlin compiler older than 2.2 makes those methods abstract, a different ABI. Not checked.

## Observations that are not bugs

Before 1.0, compatibility is not guaranteed ([0016](../decisions/0016-public-api.md)), so the following are not bugs. Each makes a likely future change break apps compiled earlier once 1.0 is reached, and is cheaper to change before then. They were decided on 2026-10-16: adding parameters in [0036](../decisions/0036-adding-parameters.md), data classes, constants, and enums and sealed types in [0037](../decisions/0037-api-shape-before-1.0.md), and the versions of the artifacts in [0018](../decisions/0018-distribution.md).

- Data classes with public constructors in what vtfx returns: `TerminalModes`, `CursorState`, `Hyperlink`, `TerminalLink.Explicit` and `Matched`, and `TerminalLinkClick`. A new property (a new mode; the position of a link click, which [0031](../decisions/0031-desktop-pointer-and-terminal-state.md) foresees) changes the signatures of the constructor and `copy`.
- New parameters of `Terminal` and of the `TerminalSession` constructor, and new properties of `TerminalStyle`, `TerminalColors`, `GatePolicy`, and `TerminalLimits` (their constructors, and `copy` where there is one), change the JVM signature even with a default value. Keeping old callers working needs the old signature kept as a hidden overload; [0036](../decisions/0036-adding-parameters.md) now decides this for 1.0 on.
- Public `const val`s are copied into apps (R1): the bounds `TerminalLimits.MAX_*` cannot be lowered without breaking apps, and `CharWidth.UNICODE_VERSION` reports the version that an app was compiled with, not that of the tables it runs with.
- A new entry of an enum, or a new subtype of a sealed type, that vtfx hands to apps (`TerminalLink`, `MouseTracking`, `MouseEncoding`, `CursorShape`, `UnderlineStyle`) makes an exhaustive `when` compiled earlier throw `NoWhenBranchMatchedException`. 0016 does not say whether that is a breaking change.
- The six artifacts call each other's `@InternalVtfxApi` declarations, which may change in any version (0016), and are published separately ([0018](../decisions/0018-distribution.md)). A Gradle resolution that mixes their versions can fail with `NoSuchMethodError`.

Positive findings: `TerminalSnapshot` and `LineSnapshot` have internal constructors, the interfaces that apps implement take new methods with default bodies compatibly (JVM default methods), and no public declaration is `inline`, so no function bodies are copied into apps.
