### [CORE-1] Image placements on the alternate screen (or when `scrollbackLines = 0` or `scrollTop > 0`) are immediately destroyed when their top line scrolls off `scrollTop`, including when placing a full-screen image at `(0, 0)`

- Severity: High
- Status: Fixed
- File: `vtfx-core/src/main/kotlin/com/google/vtfx/core/Emulator.kt:882-901`, `vtfx-core/src/main/kotlin/com/google/vtfx/core/ScreenBuffer.kt:107-117`, `vtfx-core/src/main/kotlin/com/google/vtfx/core/graphics/Graphics.kt:402-403`
- Reproduction test: `ReviewReproTest.reproCore1_alternateScreenFullScreenPlacementIsDestroyedImmediatey`

#### Problem

Non-virtual image placements are anchored to the `Line` (or `CompactLine`) of their top-left cell (`Graphics.kt:402`). When `ScreenBuffer.scrollUp` scrolls lines off `top` without saving them to `scrollback` (`scrollback == null || !saveToScrollback || top != 0 || scrollback.maxLines == 0`), it immediately invokes `this[top + i].killAnchors()` (`ScreenBuffer.kt:116`), which deletes every placement anchored to those lines even when the remaining rows of a multi-row placement (`row + placement.rows > 0`) are still on the visible screen.

In particular, in `Emulator.moveCursorAfterImage(columnsSpanned, rowsSpanned)` (`Emulator.kt:882-901`), when a placement with default cursor policy (`C=0`) reaches the right edge of the screen (`x = cursorX + columnsSpanned >= columns`), `x` wraps to `0` and `y` is incremented (`y = cursorY + rowsSpanned`). Consequently, when a full-screen TUI program on the alternate screen (`\e[?1049h`) — or on the main screen with `TerminalLimits(scrollbackLines = 0)`, or inside a `DECSTBM` scrolling region with `scrollTop > 0` — places an image spanning the full width and height of the screen/region (`c = columns, r = rows`) at `(0, 0)` (or `scrollTop`), `moveCursorAfterImage` computes `y = scrollBottom + 1` and scrolls up by 1 line (`screen.scrollUp(scrollTop, scrollBottom, 1, ...)`). That scroll immediately calls `killAnchors()` on row `scrollTop`, destroying the placement that `Graphics.place` just created on the line before (and if the image was transmitted without an explicit `i=` or `I=`, deleting the `StoredImage` as well). The same happens whenever any multi-row image (`r >= 2`) anchored at row `0` on the alternate screen (or when `scrollbackLines = 0`) is scrolled up by 1 line, or when an image taller than `scrollbackLines + 1` on the main screen has its top line evicted from the scrollback while its bottom rows are still on the screen.

#### Expected behavior

Per [docs/design/emulation.md](../design/emulation.md) section 9.5, [docs/decisions/0038](../decisions/0038-kitty-graphics.md), and [docs/research/kitty-graphics-programs.md](../research/kitty-graphics-programs.md), a multi-row placement whose top row has scrolled above the screen (or scrollback) while its remaining rows are still on the screen — including a full-screen placement (`c = columns, r = rows`) placed at `(0, 0)` on the alternate screen — must remain visible and alive as long as its bottom edge is still within the screen (or scrollback).

#### Verification

`./gradlew --console=plain --no-configuration-cache -I docs/reviews/repro-2026-10-22-core/review.init.gradle :vtfx-core:reviewRepro --tests "*reproCore1*"` fails at `ReviewReproTest.kt:52` (`expected:<1> but was:<0>`).

#### Resolution

Fixed in `795d5317dd514727e51aa29297cdf891d7e75657` (scrolling) and `a84a4c1f4adc568fd86d5a56d208833a7a7a2506` (resizing, which drops the lines beyond the scrollback's capacity). When the line of a placement scrolls off the top of the screen without going to the scrollback (the alternate screen, `scrollbackLines = 0`) or leaves the scrollback, also when the size changes, the anchor moves down to the line that takes its place, with `Placement.rowsAbove` counting the image rows above it; the placement goes once no row is left. Deleted lines and scrolling regions below the top still delete their placements, since images are not cut at the margins; this part of the report (`scrollTop > 0`) is a provisional choice recorded in [decisions/0069](../decisions/0069-placements-scrolled-off-the-top.md). Tests that failed before the fix: `ReviewReproTest.reproCore1_alternateScreenFullScreenPlacementIsDestroyedImmediatey`, and in `GraphicsTest$FollowingTheText` `aFullScreenImageOnTheAlternateScreenStaysAfterTheCursorScrolls`, `scrollingTheWholeScreenOffKeepsAnImageThatIsTallerThanIt`, `placementsLeavingTheScrollbackStayWhileTheirLastRowIsKept`, `withoutAScrollbackPlacementsStayWhileRowsAreOnTheScreen`, `placementsWhoseTopRowScrolledOffAreFoundByTheirRows`, `shrinkingWithoutAScrollbackKeepsPlacementsWithRowsLeft`, `shrinkingKeepsPlacementsWhoseRowsAreLeftInTheScrollback`.

### [CORE-2] Placing an image taller than the scrolling region (`y - scrollBottom > height`) clamps the scroll count to `height`

- Severity: Medium
- Status: Open
- File: `vtfx-core/src/main/kotlin/com/google/vtfx/core/Emulator.kt:889-899`, `vtfx-core/src/main/kotlin/com/google/vtfx/core/ScreenBuffer.kt:107-117`
- Reproduction test: `ReviewReproTest.reproCore2_imageTallerThanScreenDoesNotScrollFarEnough`

#### Problem

When a non-virtual image placement with `C=0` has `y > scrollBottom`, `Emulator.moveCursorAfterImage` (`Emulator.kt:890-896`) calls `screen.scrollUp(scrollTop, scrollBottom, y - scrollBottom, style, saveToScrollback = true)`. However, `ScreenBuffer.scrollUp` (`ScreenBuffer.kt:108`) clamps the scroll count to the height of the scrolling region (`val n = minOf(count, height)`). When the image spans more rows than the height of the screen/scrolling region (for example, placing an image with `r = 12` at row `0` of a 5-row screen, where `y = 11`, `scrollBottom = 4`, and `y - scrollBottom = 7 > 5`), `ScreenBuffer.scrollUp` pushes only `5` lines into the scrollback instead of `7`. The placement's anchor ends up at `row = -5` instead of `row = -7`, so the image extends `2` rows below the bottom of the 5-row screen (`-5 + 12 = 7 > 5`) and the cursor at `row = 4` is not on the last row of the image.

#### Expected behavior

Per [docs/design/emulation.md](../design/emulation.md) section 9.5 and [docs/decisions/0038](../decisions/0038-kitty-graphics.md), placing an image with `C=0` scrolls by `y - scrollBottom` rows so that the last row of the image lands on `scrollBottom` (with the cursor on that row) and `y - scrollBottom` lines enter the scrollback.

### [CORE-3] `Line.breakWide` does not clear `links`, `underlineColors`, or (on erase/insert/delete) `styles` on the orphaned blank half of a split wide character

- Severity: Medium
- Status: Open
- File: `vtfx-core/src/main/kotlin/com/google/vtfx/core/Line.kt:294-334`, `vtfx-core/src/main/kotlin/com/google/vtfx/core/Line.kt:452-460`
- Reproduction test: `ReviewReproTest.reproCore3_breakingWideCharacterLeavesHyperlinkUnderlineColorAndStyleOnBlankHalf`

#### Problem

When an operation splits a two-cell wide character, `Line.breakWide(column)` (`Line.kt:452-460`) only sets `codes[otherHalf] = BLANK` (and `clusters[column - 1] = null` when `column` is `WIDE_TAIL`). Unlike `Line.resized` (`Line.kt:421-425`) and `Line.fillBlank` (`Line.kt:432-438`), `breakWide` does not clear `links` or `underlineColors`, and `erase`, `insertBlanks`, and `deleteChars` do not apply `fillBlank` to the broken half outside the erased range:

1. In `set`, `setNarrow`, and `makeWide`, overwriting one half of a wide character leaves the other (now blank) half with its old `links` (OSC 8 hyperlink ID) and `underlineColors` (SGR 58).
2. In `erase` (`ECH`, `EL`, `ED`), erasing one half of a wide character leaves the other half with its old `styles` (old background color instead of the current BCE background, plus underline/inverse/invisible flags), old `links`, and old `underlineColors`.
3. In `insertBlanks` (`ICH`, `Line.kt:309-317`), inserting blanks at the right half (`WIDE_TAIL`) of a wide character leaves `styles[column]`, `links[column]`, and `underlineColors[column]` on cell `column` and shifts them right by `n` columns via `shift(column, column + n, ...)`, while also leaving `styles[column - 1]`, `links[column - 1]`, and `underlineColors[column - 1]` on cell `column - 1`.
4. In `deleteChars` (`DCH`, `Line.kt:326-334`), deleting cells ending at the left half (`isWideHead(column + n - 1)`) of a wide character leaves `styles[column + n]`, `links[column + n]`, and `underlineColors[column + n]` on cell `column + n` and shifts them left to `column`.

#### Expected behavior

Per [docs/design/emulation.md](../design/emulation.md) section 7.2 (*"An operation that splits one (printing over, erasing, or deleting one half of it, or inserting cells at its right half) erases both halves"*), section 8.1 (*"Erased cells have no underline color"*), section 6 (*"`bce` is erasing with the background color"*), and `LineSnapshot.underlineColorAt` KDoc (*"It is the default for a cell that is not underlined"*), the broken half of a split wide character must not retain hyperlinks, underline colors, or stale styles from the destroyed wide character.

### [CORE-4] `Line.compact()` loses background colors of blank cells erased before the end of the line when scrolled into the scrollback

- Severity: Medium
- Status: Open
- File: `vtfx-core/src/main/kotlin/com/google/vtfx/core/Line.kt:250-254`, `vtfx-core/src/main/kotlin/com/google/vtfx/core/Line.kt:371-409`, `vtfx-core/src/main/kotlin/com/google/vtfx/core/Line.kt:519-531`
- Reproduction test: `ReviewReproTest.reproCore4_scrollbackCompactionLosesBackgroundOfBlankCellsBeforeEndOfLine`

#### Problem

`Line.compact()` (`Line.kt:371-409`) determines `val end = contentEnd()`, which scans backward only while `codes[end - 1] == BLANK` (`Line.kt:250-254`) without checking `styles`. It then copies only `styles.copyOf(end)` and records `trailingStyle = styles[codes.size - 1]` for all remaining blank cells in `end until columns`. When `CompactLine.expand()` (`Line.kt:520`) reconstructs the line, every blank cell in `end until columns` receives `trailingStyle` (`styles[columns - 1]`).

Consequently, whenever blank cells after the last graphic character do not all share the style of column `columns - 1` — for example, when a range of cells before the right edge is erased with a colored background via `ECH` (`CSI X`), `EL 1` (`CSI 1 K`), `ED 1` (`CSI 1 J`), `ICH` (`CSI @`), or `DCH` (`CSI P`), or when `EL 0` (`CSI K`) erases with one background color and a later `EL 0` near the end of the line erases with another — scrolling the line into the scrollback overwrites the styles of all blank cells in `end until columns` with `styles[columns - 1]`.

#### Expected behavior

Per [docs/design/emulation.md](../design/emulation.md) section 6 (`bce`) and `CompactLineTest` (*"Checks that the scrollback's CompactLine gives back the line it was made from"*), compacting and expanding a scrollback line must preserve the background style of every cell on the line (`line.compact().expand().contentEquals(line)` must hold for any line).

### [CORE-5] `Parser` does not exit `CSI_IGNORE` or reject `DCS` final bytes on non-ASCII code points (`> 0x7E`), swallowing subsequent terminal output

- Severity: Medium
- Status: Open
- File: `vtfx-core/src/main/kotlin/com/google/vtfx/core/parser/Parser.kt:236-279`, `vtfx-core/src/main/kotlin/com/google/vtfx/core/parser/Parser.kt:391-395`
- Reproduction test: `ReviewReproTest.reproCore5_nonAsciiInCsiIgnoreOrDcsSwallowsSubsequentOutput`

#### Problem

[docs/design/emulation.md](../design/emulation.md) section 2 and [docs/decisions/0001](../decisions/0001-parser.md) specify that after UTF-8 decoding, a code point beyond ASCII (`> 0x7E`) where an escape or control sequence expects its final byte ends the sequence without dispatching it and returns to `GROUND`. While `escDispatch` (`Parser.kt:380`) and `csiDispatch` (`Parser.kt:386`) enforce `if (final > ASCII_LAST) return` and set `state = GROUND`, two places in `Parser.kt` do not handle `c > ASCII_LAST`:

1. In `CSI_IGNORE` (`Parser.kt:236-241`), only `c in 0x40..0x7E` transitions to `GROUND`. If a malformed CSI sequence (such as `\e[??` or `\e[1?`) is followed by non-ASCII characters (such as CJK text `"あいう"` or `U+FFFD`), `CSI_IGNORE` stays in `CSI_IGNORE` and swallows all non-ASCII characters, spaces, digits, and punctuation (`0x20..0x3F`) until an ASCII byte in `0x40..0x7E` or `ESC`/`CAN`/`SUB` arrives.
2. In `DCS_ENTRY`, `DCS_PARAM`, and `DCS_INTERMEDIATE` (`Parser.kt:258, 270, 278`), `else -> dcsHook(c)` does not check `c > ASCII_LAST`. If a non-ASCII code point (or `U+FFFD` from a truncated UTF-8 lead byte such as `0xC3` inside `ESC P`) arrives where the DCS final byte is expected, `dcsHook` accepts it as `dcsFinal` and enters `DCS_PASSTHROUGH`, swallowing all subsequent terminal output into the DCS string until `ST` (`ESC \`), `ESC`, `CAN`, or `SUB` arrives (and if closed by `ST` within `maxStringLength`, calling `handler.dcsDispatch` with `final > 0x7E`).

#### Expected behavior

Per [docs/design/emulation.md](../design/emulation.md) section 2 and [docs/decisions/0001](../decisions/0001-parser.md), a code point `> 0x7E` in `CSI_IGNORE`, `DCS_ENTRY`, `DCS_PARAM`, or `DCS_INTERMEDIATE` must end the sequence without dispatching it and return to `GROUND` (just as `CSI_ENTRY`, `CSI_PARAM`, and `CSI_INTERMEDIATE` do in `ParserTest.aTruncatedUtf8SequenceInACsiDoesNotTakeTheDigitsAfterIt`).

### [CORE-6] `Terminal.reset()` does not reset `Parser` (or `Utf8Decoder`), leaving unclosed string sequences active across a reset

- Severity: Medium
- Status: Open
- File: `vtfx-core/src/main/kotlin/com/google/vtfx/core/Terminal.kt:121-124`, `vtfx-core/src/main/kotlin/com/google/vtfx/core/parser/Parser.kt:80-89`
- Reproduction test: `ReviewReproTest.reproCore6_terminalResetLeavesParserInUnclosedStringState`

#### Problem

`Terminal.reset()` (`Terminal.kt:122-124`) calls `emulator.reset()` but does not reset `parser` (or its `Utf8Decoder`). When `RIS` (`ESC c`) arrives via `Terminal.write`, the `ESC` and `c` bytes transition `parser` back to `GROUND` before invoking `emulator.reset()`. By contrast, when `Terminal.reset()` (or `TerminalSession.reset()`) is called programmatically while `parser` is inside an unclosed `OSC_STRING`, `DCS_PASSTHROUGH`, `APC_STRING`, `SOS_PM_STRING`, `CSI`, or `ESCAPE` state (or while `Utf8Decoder` is mid-sequence):

1. Output written after `terminal.reset()` continues to be consumed by the pre-reset parser state (for example, all plain text written after `reset()` is swallowed into an unclosed `OSC`, `DCS`, `APC`, or `SOS`/`PM` string).
2. When `BEL` or `ST` (`ESC \`) later arrives after `terminal.reset()`, `Parser.exitState()` dispatches the buffered pre-reset `OSC`, `DCS`, or `APC` command (such as changing the window title, requesting an OSC 52 clipboard write, or executing a graphics command) onto the freshly reset terminal.

#### Expected behavior

Per `Terminal.reset()` KDoc (`"Resets the terminal to its initial state, as RIS does. The scrollback is kept."`) and [docs/design/emulation.md](../design/emulation.md) section 10.1, `Terminal.reset()` must also reset `parser` (and `Utf8Decoder`) to the initial `GROUND` state and discard any partial sequence or string.

### [CORE-7] `SearchIndex` loses matches on surviving scrollback lines when the first row of a wrapped scrollback line is evicted

- Severity: Medium
- Status: Open
- File: `vtfx-core/src/main/kotlin/com/google/vtfx/core/Search.kt:185-186`, `vtfx-core/src/main/kotlin/com/google/vtfx/core/Search.kt:206-210`
- Reproduction test: `ReviewReproTest.reproCore7_searchIndexLosesMatchOnSurvivingWrappedRowAfterFirstRowLeavesScrollback`

#### Problem

When autowrap joins multiple scrollback rows (e.g., line `0` and line `1`) into a single `SearchText(firstLine = 0, lastLine = 1)`, `SearchIndex` searches their concatenated text using non-overlapping KMP matching (`LiteralFinder.find`, `Search.kt:322-335`) and stores the `SearchText` in `texts`. When the scrollback is full and evicts line `0` (`oldestLine = 1`) while line `1` remains in the scrollback:

1. `SearchIndex.update` (`Search.kt:206-210`) removes `texts.first()` only when `texts.first().lastLine < oldestLine` (keeping the un-trimmed `SearchText(0..1)` in `texts`), and removes matches from `kept` where `kept.first().firstLine < oldestLine`.
2. If a match started on the evicted line `0` and extended into line `1` (e.g., `"fofo"` matching `0:2-1:2` in `"xxfo"` + `"fofo"`), non-overlapping matching skipped the overlapping match `1:0-1:4` on line `1`. Once line `0` is evicted (`oldestLine = 1`), `0:2-1:2` is dropped because `firstLine (0) < oldestLine (1)`, and the surviving rows of `SearchText` (`1..lastLine`) are never re-searched without line `0`. As a result, `index.matches` misses the match `1:0-1:4` on surviving line `1`.
3. For the same reason, calling `index.withQuery(newQuery)` (`Search.kt:186`) after line `0` is evicted searches the un-trimmed `SearchText(0..1)` including the evicted row `0`: before `update` is called, `withQuery` returns matches on evicted lines (`firstLine < oldestLine`), and even after `update` is called, matches starting on evicted row `0` can overlap and suppress valid matches on surviving row `1`.

#### Expected behavior

Per `SearchIndex` KDoc (`Search.kt:107-120`) and [docs/decisions/0047](../decisions/0047-search.md), `SearchIndex.update` and `SearchIndex.withQuery` must report the same matches over the lines currently retained in the scrollback and screen as a fresh `SearchIndex` over the terminal.

### [CORE-8] `Terminal.write` range check overflows 32-bit signed `Int`

- Severity: Low
- Status: Open
- File: `vtfx-core/src/main/kotlin/com/google/vtfx/core/Terminal.kt:98-103`
- Reproduction test: `ReviewReproTest.reproCore8_writeRangeCheckOverflowsInt`

#### Problem

`Terminal.write` validates its range with:
```kotlin
require(offset >= 0 && length >= 0 && offset + length <= bytes.size) {
    "range out of bounds"
}
```
When `offset > 0` and `length > Int.MAX_VALUE - offset` (e.g., `offset = 1, length = Int.MAX_VALUE`), `offset + length` overflows to a negative `Int`, which passes `offset + length <= bytes.size`. `Parser.parse` then computes `val end = offset + length` (also negative), so `while (i < end)` exits immediately without parsing or throwing `IllegalArgumentException` (unlike `PngDecoder.checkRange` at `PngDecoder.kt:120` and `Zlib.inflate` at `Zlib.kt:41`, which check `offset <= data.size - length`).

#### Expected behavior

Per [docs/design/emulation.md](../design/emulation.md) section 10.1 and `TerminalSession.feed` KDoc (`@throws IllegalArgumentException if [offset] and [length] are not within [bytes]`), `Terminal.write` must throw `IllegalArgumentException` whenever `offset > bytes.size - length`.

### [CORE-9] `CSI S` (`SU`), `CSI T` (`SD`), `CSI L` (`IL`), and `CSI M` (`DL`) replace the line under the cursor without incrementing `Terminal.lineChanges`

- Severity: Low
- Status: Open
- File: `vtfx-core/src/main/kotlin/com/google/vtfx/core/Emulator.kt:484-492`, `vtfx-core/src/main/kotlin/com/google/vtfx/core/Emulator.kt:769-779`
- Reproduction test: `ReviewReproTest.reproCore9_scrollingCommandsDoNotIncrementLineChanges`

#### Problem

`Terminal.lineChanges` is used by `TerminalSession` to detect when host output moved the cursor to another logical line even if the cursor's row coordinate did not change ([docs/design/ime-contract.md](../design/ime-contract.md) section 5.1: *"Reset when the screen scrolls and the cursor's row number does not change, as with a newline on the bottom row, or when the cursor moves to another line and back within one receive (`Terminal.lineChanges`)."*). ### [CORE-11] Open screen matches (`closing = false`) that push `kept.size` past `SearchIndex.MAX_MATCHES` permanently evict closed scrollback matches from `kept` and leave `isCapped` permanently `true`

- Severity: Medium
- Status: Open
- File: `vtfx-core/src/main/kotlin/com/google/vtfx/core/Search.kt:206-213`, `vtfx-core/src/main/kotlin/com/google/vtfx/core/Search.kt:260-272`
- Reproduction test: `ReviewReproTest.reproCore11_openScreenMatchesExceedingMaxMatchesPermanentlyEvictClosedScrollbackMatches`

#### Problem

`SearchIndex` stores both closed scrollback matches (the first `closedCount` entries) and open screen matches (`closing = false`) in a single deque `kept` capped at `MAX_MATCHES` (`1000`). In `SearchIndex.add(closing, match)` (`Search.kt:260-272`):
```kotlin
kept.addLast(match)
if (kept.size <= MAX_MATCHES) return
val dropped = kept.removeFirst()
// The oldest match is of a line in texts, or else of the line being searched.
if (closedCount > 0 || closing) {
    if (closedCount > 0) closedCount--
    droppedClosedLine = maxOf(droppedClosedLine, dropped.firstLine)
} else {
    droppedOpen = true
}
```
When searching open lines on the screen (`closing = false`), if the combined count of closed scrollback matches and open screen matches exceeds `MAX_MATCHES`, `add(closing = false, match)` removes the oldest closed scrollback matches from the front of `kept`, decrements `closedCount`, and sets `droppedClosedLine = maxOf(droppedClosedLine, dropped.firstLine)`.

When the screen is subsequently modified or cleared (e.g., `\e[2J`), `SearchIndex.update` (`Search.kt:212`) runs `while (kept.size > closedCount) kept.removeLast()`, which discards all the open screen matches without restoring the closed scrollback matches from `texts` that those temporary screen matches displaced, and without resetting `droppedClosedLine`. Consequently, scrollback matches are permanently missing from `index.matches` (even leaving `index.matches` completely empty when `1000` screen matches were displayed and then cleared), and `index.isCapped` remains `true` (`droppedClosedLine >= oldestLine`) even when the terminal has far fewer than `MAX_MATCHES` matches in total.

#### Expected behavior

Per `SearchIndex` KDoc (`Search.kt:107-120`, `173-179`) and [docs/decisions/0047](../decisions/0047-search.md), `SearchIndex.matches` must keep the newest `MAX_MATCHES` matches currently in the terminal, and `isCapped` must be `false` whenever the total number of matches in the terminal is at most `MAX_MATCHES`. Temporary matches on the screen that are later overwritten or erased must not permanently delete closed scrollback matches or leave `isCapped` stuck at `true`.

### [CORE-12] Replacing an existing image by ID (`i=<id>`) runs `makeRoom` before freeing the replaced image, evicting unrelated older images

- Severity: Medium
- Status: Open
- File: `vtfx-core/src/main/kotlin/com/google/vtfx/core/graphics/Graphics.kt:180-192`, `vtfx-core/src/main/kotlin/com/google/vtfx/core/graphics/Graphics.kt:281-286`, `vtfx-core/src/main/kotlin/com/google/vtfx/core/graphics/GraphicsLayer.kt:72-76`
- Reproduction test: `ReviewReproTest.reproCore12_replacingImageByIdEvictsUnrelatedImageBeforeFreeingReplacedImage`

#### Problem

When transmitting an image with an explicit `command.imageId` (`i=<id>`) that already exists in `screen.layer`, `GraphicsLayer.add(stored)` (`GraphicsLayer.kt:72`) deletes the existing image with that ID (`if (image.id != 0L) imagesById[image.id]?.let { delete(it) }`), freeing its bytes and placements.

However, in `Graphics.finish` (`Graphics.kt:180-192`), `makeRoom(screen.layer, bytes)` is called *before* `screen.layer.add(stored)` deletes the existing image with `command.imageId` (unlike `GraphicsLayer.add(placement)` at `GraphicsLayer.kt:101-113`, which removes the replaced placement with the same ID before checking `MAX_PLACEMENTS`). Because `this.bytes` and `layer.imageCount` still include the old image with `command.imageId` while `makeRoom` runs:
1. If `this.bytes + bytes > maxBytes` (even though `this.bytes - oldImage.bytes + bytes <= maxBytes`), `makeRoom` calls `evict(layers)`, which deletes the *oldest* image in the terminal (such as an unrelated image `i=1` placed earlier) before `screen.layer.add(stored)` deletes the old `command.imageId` image as well.
2. Likewise, if `layer.imageCount == MAX_IMAGES` (`1024`), replacing an existing image ID causes `makeRoom` to evict the oldest image in `layer` before `add` also deletes the replaced image, leaving `1023` images instead of `1024`.

#### Expected behavior

Per [docs/design/emulation.md](../design/emulation.md) section 9.4 and [docs/decisions/0038](../decisions/0038-kitty-graphics.md), replacing an existing image with the same `i=<id>` must account for (or delete) the image being replaced before evicting other images to fit within `maxImageBytes` and `MAX_IMAGES`.

- **Additional design/robustness observations (non-bug / minor edge cases)**:
  - **`LineSnapshot.underlineColorAt` on image placeholders**: `LineSnapshot.underlineColorAt` KDoc (`TerminalSnapshot.kt:85-87`) states *"It is the default for a cell that is not underlined"*, whereas [docs/design/emulation.md](../design/emulation.md) section 8.1 notes *"The exception is the placeholder of an image, which keeps the underline color without an underline, since it gives the placement id"*. Updating the KDoc on `LineSnapshot.underlineColorAt` to mention image placeholders would avoid ambiguity for callers.
  - **`UrlMatcher` word-boundary check with supplementary characters (`Links.kt:90`)**: `if (start > 0 && text[start - 1].isLetterOrDigit()) continue` checks a single UTF-16 `Char` (`text[start - 1]`). When a supplementary Unicode letter or digit (above `U+FFFF`, such as `𠮷` `U+20BB7` or mathematical letters `U+1D400..U+1D7FF`) immediately precedes `http://...`, `text[start - 1]` is a low surrogate (`\uDC00..\uDFFF`), for which `Char.isLetterOrDigit()` is `false`, whereas `Character.isLetterOrDigit(text.codePointBefore(start))` is `true`.
  - **`Placeholders.resolve` when non-placeholder combining marks follow `U+10EEEE` (`Placeholders.kt:74-79`)**: If a combining mark outside `PlaceholderDiacritics.CODE_POINTS` is attached to `U+10EEEE`, `binarySearch` returns a negative value clamped to `-1` while still incrementing `count`, preventing the cell from inheriting row/column/highByte from `left` under the `count == 0` / `count == 1` / `count == 2` rules.
  - **`Reflow` when dropping a wide character at `newColumns = 1` on a wrapped line with an image anchor (`Reflow.kt:82-93`)**: When a wide character is skipped at `newColumns = 1` (`c += width; continue`), any image placement anchored to that wide character's cells is not processed in the `while (c < contentEnd)` loop; if no narrow character follows on that row, the post-loop anchor handler attaches it to `current` (which may still be the full preceding row of a wrapped line).
